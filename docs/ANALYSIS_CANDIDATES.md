# 分析候选保留与人工处理

五类分析（需求、代码、变更、用例生成、用例分析）统一遵守：模型返回是候选数据，局部字段冲突或校验失败不导致原始候选不可见。API、Codex CLI共用相同业务入口。保存候选不等于人工认可或测试通过；任何修正均不调用模型，不自动应用用例。

## 共同候选工作区

需求、代码、变更（完整输入任务）、用例分析在原记录提供“候选与待处理问题”。项目鉴权、逻辑删除、发起人权限均在各模块复查；原始候选及人工草稿只允许发起人查看/修订。原有报告共享与原文下载权限不扩大。正在执行的任务不可处理；成功报告不可通过此入口覆盖。

`modules/candidate_results`仅承担无损JSON成员展示、重复字段及各冲突值提取、草稿摘要/并发检查、不可变私有文件和审计；不导入HTTP或数据库，也不作业务判断。各模块的`candidate_review`负责路由背后的授权、固定来源检查、完整原契约校验和正式结果保存。直接导入仍严格拒绝重复键，不把“最后一个值覆盖前值”作为修复。

GET/POST路径分别是原记录路径追加`/candidate-review`；需求为`requirements/risk-analyses/{id}/candidate-review`。POST需`request_id`、`base_sha256`、`candidate_json`、非空`reason`及`confirmed=true`。重复请求幂等，不同内容复用UUID或旧摘要冲突返回409。来源/权限检查失败直接拒绝，不能借保存草稿越权。

草稿保存在私有`document_storage_path`同级的`candidate-reviews/`，文件名固定为模块/记录ID/随机UUID，不接收任意路径；历史描述符含文件哈希、原始响应哈希、修订哈希、作者/时间/说明及校验结果。描述符追加在已有metadata/context的`candidate_review_history`中；数据库不保存新增原始响应正文。篡改文件/摘要或错误记录关联不能读取。原件不覆盖，每次修订独立保存。

完整校验不通过的修订仍保存为可见草稿，任务保留FAILED及具体原因，原报告不变；通过后用各模块原有存储机制保存正式报告并保留全部历史。代码、变更及用例分析递增原revision。需求分析创建/复用原风险报告存储，保留其处理与重复报告规则。免费处理不要求再次消耗AI配置，不发送请求。

工作区展示全部可解析的顶层数组候选（20条分页）、原JSON、重复键路径和值、整体校验原因及人工处理记录。由于这四类报告有跨项引用/覆盖关系，不能仅删除出错节点就冒充整份校验成功；可见候选仍需完整校验，不伪造“已验证”的结论。JSON无法解析时原文仍可见并可人工修订。旧分批变更继续使用原历史候选下载/重校验，不静默改写原分批计划。

## 用例生成逐条隔离

契约3的cases/notes分别独立校验，局部重复键、必需字段缺失、非法来源等保存在私有不可变delivery文件中。可独立通过的建议照常保存、展示和人工审核入库；问题项在现有“冲突与待澄清”中展示全部原字段/冲突值/错误原因，不能直接应用。完整根结构或输入校验失败时保存整体问题原文，不猜测缺失内容。

平台报告增加可选`source_indices`审计（原cases/notes序号与总数），原序号生成稳定C/Q及摘录证据key；修正第二项不会把第三项重编号。存储报告仍由原输入/model_output重算核验，缺失问题项使outcome为PARTIAL。成功历史报告不改写。

POST `case-generation/{run_id}/batches/{batch_id}/candidate-issues/{issue_id}/resolve`需原revision、请求UUID、修正JSON或ignored=true、处理说明及confirmed=true。锁定原run/batch并复查发起人、状态、版本、来源；已保存有效建议必须逐字保持同一key/内容。修正后须通过全部本项契约才进入建议；忽略仍保留原候选和理由。每次操作追加新delivery快照/历史指针；原响应、此前人工处理、已应用用例不覆盖。已修正项不能再经此入口改动，继续走已有建议编辑/审核流程。

旧FAILED生成记录可手动免费“重新校验”建立问题展示；不自动扫描或重写成功历史记录。已按用户选择恢复P1的历史记录保持原处理。
