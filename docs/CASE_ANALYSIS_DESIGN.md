## 1. 定位与现状

用例分析回答三个问题：现有用例是否符合所选需求；本次用例范围还缺哪些明确场景；已有用例的步骤、准备和预期是否足够清楚。

已确认方向来自[整体工作台方案](LOCAL_ANALYSIS_SESSION_PLAN.md)与[其他分析方案](OTHER_ANALYSIS_DESIGN.md)：检查需求符合性、遗漏与设计质量，区分需求不清与用例错误，不以覆盖率为主，不承担执行失败根因分析。需求、原型或用例不足时明确限制，不能把设计分析称为实际测试通过。

本轮只读核对：正式 `frontend/src/App.tsx` 保留 `/coverage`「用例分析」菜单，由通用 Pending 页面承接；用例管理和用例生成已有正式能力。总HTML原型仍包含早期验收点/覆盖演示，不能当作本方案已确认布局。保留菜单名称、路径、顺序；批准改原型后直接同步总HTML与仓库审阅副本。

与其他模块的分工：

| 模块 | 本职工作 |
| --- | --- |
| 需求分析 | 找需求不完整、矛盾、待明确的业务规则 |
| 用例生成 | 按需求首次设计或维护用例，输出可审核草案 |
| 用例分析 | 审查已有用例，找偏差、遗漏和设计问题，给出改进建议 |
| 代码分析 | 核对实现、调用链与前后端衔接 |
| 变更分析 | 对照旧新版本，分析变化影响及归因 |

用例分析可独立发起，不强制先完成需求分析，不重新生成整套用例，也不重复进行代码检查。

## 2. 两种审查方式

默认「对照需求分析」，另提供「仅检查用例质量」。

| 方式 | 必需输入 | 可以判断 | 判断边界 |
| --- | --- | --- | --- |
| 对照需求分析 | 至少一份实际可读取的需求或原型，以及明确用例范围 | 需求偏差、缺失场景、设计问题、依据冲突 | 结论仅针对所选资料和用例；需求未明确时先澄清 |
| 仅检查用例质量 | 至少一条完整设计快照 | 步骤含糊、预期不可判断、条件自相矛盾、明显重复等 | 无需求依据时不能判符合需求、需求缺失或用例过时 |

对照方式允许所选范围为0条，但必须明确确认「本次没有现有用例，仅识别应补充的场景」。不能把列表读取失败、尚未加载或无权限误当0条。仅有URL、文件名或编号清单不能开始分析。

用例来源为本项目用例管理；导入、手工、AI生成用例一视同仁，无历史生成记录门槛。默认只选活动用例；停用用例可显式加入并展示状态，已删除用例不进入新分析。停用用例不作为活动测试集已有场景的充分依据。

## 3. 用户流程与输入

流程：新建分析 → 选择方式、资料与用例 → 读取并固定输入 → 核对范围及本人AI → 开始分析 → 审阅问题 → 记录处理或准备用例草案 → 人工审核入库 → 按需要复核。

新建弹窗保持一次表单，字段顺序如下：

1. 分析名称、审查方式。
2. 需求/原型资料及固定版本；原型按页面选择，对应及公共批注同次读取。
3. 用例范围：全部活动用例、分类/搜索结果、已勾选用例；后两种支持跨页，明确实际条数。
4. 功能关注范围与补充关注点，可留空表示审查全部所选内容。
5. 可选带入已有分析的相关人工结论，展示来源；风险摘要不能替代原始需求。

「读取资料并准备分析」只读取和固定内容，不调用AI。期间显示真实读取状态，阻止重复点击；失败留在弹窗、保留选择并显示原因。准备成功后展示资料/页面/批注数量、用例条数、过滤条件、文本token粗估及本人配置，用户点击「开始分析」才发起收费调用。

建议沿用用例生成的完整正文单次调用思路：需求正文和批注保持完整，用例带实际设计字段；不增加前置AI提炼、规则树、场景树或自动分批。输入过大明确提示继续或缩小范围；超过实际平台限制拒绝准备，不能截断后称全量。可信模型容量未配置时不猜硬限制，附件用量另计。

后台固定资料内容/版本/哈希、页面与批注、选择条件、完整用例设计、内部 `case_id`、设计版本、生命周期与分类快照，以及Skill版本/指令/哈希和人工结论来源。展示编号允许重复，只作展示，不能用于定位修改目标。不自动携带全项目资料、聊天或其他模块结果。

## 4. 具体检查什么

| 检查项 | 典型发现 | 不能机械判错的情况 |
| --- | --- | --- |
| 需求符合性 | 需求明确禁止跨门店核销，用例预期却允许成功 | 只有经验推测、规则未明确或资料相互冲突 |
| 缺失场景 | 明确要求重复提交不重复产生记录，本次用例未找到对应检查 | 选了部分用例、未完成审查时不能扩大为全项目缺失 |
| 步骤与时序 | 未说明操作对象、关键操作顺序或状态变化时点 | 不编造页面按钮、接口或后台操作方式 |
| 预期可判断性 | 只写“操作正常”，没有可观察的状态或记录变化 | 多步对应场景级预期合法，不要求步骤/预期行数相等 |
| 前置与数据准备 | 缺角色、归属、初始状态、必要数据条件 | 缺测试账号或观察入口是准备待补，不等于业务设计错误 |
| 相互矛盾与重复 | 相同条件/动作要求相反预期，或内容重复且无独立价值 | 相同标题、不同角色/边界/时序不直接算重复 |
| 依据与适用性 | 用例引用的旧规则与当前所选依据明确不同 | 无旧新依据不能认定“本次变更引入”，没有引用不直接等于无依据 |

检查所选需求明确涉及的正向、拒绝、边界、权限、状态、时序、重复操作等适用分支；不为凑问题数强加并发/性能/安全要求，不凭通用经验认定项目有该业务规则。

问题等级用「高 / 中 / 低」表示设计风险，依据漏测或错误预期的业务后果并说明理由；它与用例P0–P4执行优先级分开。信息不足写待确认，不猜金额、频次或影响人数。

## 5. 页面与详情

建议采用当前生成/代码/变更分析熟悉的「左记录、中结果、右固定范围」三栏；这是待审阅布局，尚未替换旧总原型。

- 顶部：新建分析、导入分析结果、导出、打开用例管理。真实接入后才开放相应功能。
- 左侧：仅本模块项目记录，显示名称、方式、时间/发起人、执行状态、范围条数和问题数，支持分页与滚动。
- 中间顶部：本次范围与真实任务状态；紧凑显示用例问题、缺失场景、待澄清数量。任务失败不能显示「0问题」，部分完成不能显示整体审查完成。
- 中间三个页签：「分析问题」「用例检查」「对话」。分析问题默认显示全部，以类型、等级、处理状态和关联用例筛选/分页；不增加覆盖率大屏或总分。
- 右侧：资料名/固定版本、页面/批注数量、用例范围/条数、关注点和读取限制，只展示元信息，不铺正文。

「用例检查」列出固定输入用例，区分「AI声明已检查，本次未发现问题」「AI声明已检查，有问题」「尚未检查/无法判断」。无问题不造问题卡片；已检查声明只用于进度/追溯，不证明符合需求。0条用例时明确显示仅审查缺失场景。

问题卡片只显示标题、类型、等级、关联编号/版本、关键影响与处理状态。详情默认展示：

1. 哪里有问题、为什么影响测试。
2. 所选依据明确要求什么，以及短的相关需求/原型原文摘录，附资料名、固定版本与位置；摘录来自实际固定原文，不能用用例内容摘要冒充依据。
3. 关联用例的相关字段及版本；可展开完整前置、数据、步骤、预期等设计。多个用例矛盾时并列展示。
4. 建议如何修改/补充、哪些业务决定或执行准备仍缺少。
5. 人工处理、追问、准备修改/补充草案及历史。

仅质量检查无需求时，依据区域展示用例原字段并注明没有需求对照。原文无法唯一定位就显示限制，不自动取整份资料前几百字。原文匹配只证明摘录存在，不证明其支持结论。

详情左右外侧复用上一条/下一条交互，按当前筛选跨页顺序，首末禁用；未保存修改先保存，失败留在当前。审核排队/执行中可关闭或切换查看，不重复提交。窄屏按记录、结果、范围纵向排列，主题控件、键盘和焦点规则遵守 `UI_STANDARDS.md`。

## 6. 结果结构与完成边界

建议使用独立 `CASE_REVIEW` 契约，具体JSON需下一步Skill设计确定；不套用需求、生成或变更报告身份。简化模型正文如下，不强制逐段规则/场景覆盖表：

| 模型字段 | 内容 |
| --- | --- |
| findings | 用例问题或缺失场景：标题、类型、等级及理由、关联用例内部ID/版本/字段、描述、业务影响、建议、来源及原文摘录；可附完整用例草案 |
| notes | 业务待澄清、资料冲突/不足、执行准备待补、未完成范围及原因 |
| checked_case_ids | 模型声明已检查的输入用例ID，不创建虚假问题；平台据此展示未检查项 |
| complete | AI是否声明完成本次范围，不能解释为已证明语义覆盖或测试通过 |

任务身份、结果key、统计、未检查ID集合、版本差异、人工状态与审计由平台管理。`checked_case_ids` 必须为输入集合中的唯一ID；同一完整版本快照不以展示编号定位。notes/问题关联到用例或资料，不强迫所有说明塞进问题数量。一个问题可关联多条用例，问题数量与有问题用例数量分别计算。

合法空 `findings` 可以保存，但结论应为「本次未发现问题」或「暂时无法判断」，取决于实际限制。所有用例被列入checked也不证明所有需求场景被审查。存在未检查用例、明确未完成范围或决定性依据不足时，平台标记部分完成/材料不足，不能仅信任complete=true。

模型格式错误、引用越界、跨项目、伪造目标/版本或原文不存在时保留原始响应和安全错误，不假报报告成功。纯展示格式的无损兼容需审计；业务语义问题不能“修复”为确定事实。草案不完整不应连带丢失合法问题报告：保存问题并标明草案待补，禁止应用不合法草案。

## 7. 人工处理与用例改进

问题处理建议沿用「待确认、已确认待处理、已解决、不适用」，非待确认状态需填写结论；平台保留操作者、时间、修订和历史。已解决表示人工处理判断，不代表实际执行通过。资料澄清/执行准备说明单独展示，不占用例设计错误统计。

两个主要动作：

- 「准备修改用例」：固定目标内部ID/设计版本，在原设计上编辑建议字段，展示前后差异。
- 「准备补充用例」：创建独立候选，完整设计可直接进入人工审核；只有场景说明时先人工补齐，或由用户明确发起用例生成。

完整草案无需为了套入生成记录再调用一次AI。建议复用现有简化审核交互：左侧勾选候选、右侧完整用例、一个统一分类下拉，选项仅未分类和已有分类，单条可覆盖；底部核对并一次确认。相同场景优先关联复用，但AI语义判断不能当确定重复；仍做实际判重和人工选择。

确认后复用已明确的逐条事务规则：新增由平台编号；修改保留原编号/身份并追加设计版本；成功新增/修改已审核、未测、人员空；复用保留原分类、设计与测试历史并记录本次审核；失败继续，成功项防重放，失败由人工重新核对后重试。无实际设计变化不造新版或重置测试。问题与草案/入库映射关联，但不因入库成功自动把问题改已解决。

停止使用/合并重复用例只给理由与关联，首期由用户在用例管理按已有规则处理，不自动删除、停用或恢复；测试记录也不因分析改变。

目前 `case_generation/apply.py` 绑定生成run、候选及应用模型，不能直接称为用例分析可用接口。正式开发时各模块保留自己的权限、报告和审计；仅将确有两处使用的审核UI/预览与用例事务能力提取复用，基础写入继续使用cases公共服务，不伪造生成run/模型报告，不建立通用Agent或跨模块万能任务层。具体改造属于后续授权实施范围。

## 8. 对话、澄清与复核

用例分析拥有独立的记录/功能对话；按项目、模块、记录及功能隔离，不混入需求或生成聊天。问题追问携带所属问题、固定用例字段和相关原文，右侧明确本轮引用。

普通对话只保存消息。回复可由人工「添加为问题」或「准备为用例草案」，先进入主题表单核对，不能自动改变需求、问题状态、用例库或测试结果。

业务预期不明先保存人工澄清结论及来源，不猜默认规则；新澄清、新需求或新设计需要复核时，建立关联的新输入/分析记录，展示新旧范围，不覆盖旧报告。复核只关联用户选定的旧问题，旧问题的处理结论仍需人工确认；消失于新报告不自动等于解决。

跳转用例生成仅预填固定资料、目标用例、问题/澄清及来源，用户核对后才开始；生成缺新输入时明确拦截，不能用实时某侧冒充原固定依据。

## 9. 权限、后台、版本与异常

- 项目成员共享有权访问的记录、处理和审核，沿用现有项目权限；取消仅本次执行发起人。开始/重试/对话使用当次操作者本人有效AI配置，无平台或他人密钥回退。
- 后台建议复用 `app.chat_worker`，离开页面继续；排队、运行、完成、失败、取消与业务完整性、人工处理、审核应用分开。只展示真实阶段、耗时、接收量，不虚构百分比。
- 前端关闭/取消等待不代表上游已取消或停止计费。取消保存实际结果；重复开始、网络超时和结果不明先查状态，不自动重放。
- 失败保留固定输入、响应和安全诊断；重试由人工发起，仍使用原完整输入。新版本资料、澄清或更大范围建立新记录，不作为旧任务重试。成功项不自动再收费。
- 用例库在分析期间变化不丢弃报告；详情提示固定设计与当前版本差异。审核时重新核对权限、实际目标版本/字段、生命周期、分类和重复决定；版本冲突留草稿供人工核对，不覆盖新人工设计。
- 资料更新只提示，不暗中替换快照。源删除/失权遵守权限和固定证据保留规则，不新增向外分享、飞书采集或任意URL/Git能力；缺决定性原文明确不能复核。
- 仅测试/审核历史新增或其他用例修改不直接等于当前目标设计已变，但应重新检查实际应用条件。目标被删除/停用、分类失效等明确失败，不静默跳过后报全部成功。

## 10. 导入、导出与工程边界

导入建议沿用input.json＋report.json配对，严格关联本项目已有原件/固定快照和实际用例设计版本；不能仅核对文件名、URL、展示编号。相同内容幂等返回且保留人工处理，不静默重绑。契约、来源校验和接口正式实施后才开放入口，旧覆盖演示JSON不冒充CASE_REVIEW正式报告。

## 11. 典型例子（合成设计示例）

固定需求说明：跨门店核销应拒绝且不产生核销记录；重复核销不得重复产生记录。所选活动用例10条，其中一条预期写跨门店成功、一条重复核销只检查提示、没有手动入口场景；所选资料没有明确核销码有效时长。
