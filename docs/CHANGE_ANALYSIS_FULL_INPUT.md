# 变更分析完整输入一次分析（2026-10-26）

## 现行规则

本文适用于 v2 冻结任务和人工重试。新 v3 完整保存双侧固定输入，传输规则见 CHANGE_ANALYSIS.md。

现行 v3 规则见 [变更分析](CHANGE_ANALYSIS.md)。本文的完整发送约定适用于 v2 快照及其人工重试。

用户在分批讨论后明确要求“系统自己做的不要太多，容易丢失信息，需要的是把内容完整给AI去分析”，并质疑多次独立分析会失去整体上下文，但尚未明确选择恢复单次请求。助手已先行修改并加载本地 `FULL_INPUT` 默认方式，随后向用户明确承认这是对发送方式的推断；当前实现为可审查候选，等待用户决定是否保留。不能把本文作为用户已同意完整单次或收费调用的授权。

当前本地新建与人工重试走完整固定输入和全部原附件的一次模型请求，不再静态筛文件、剔目标、预排复核或拼接各批结论。候选已通过本地完整性及回滚测试，但完整请求此前多次400/504，不能据此保证可用。后续须由用户明确选择保留单次请求，或继续设计有清晰上下文边界的多次调用方案。

平台继续负责来源读取与项目权限、固定双侧版本/正文/哈希、根输入契约、本人AI配置、调用/取消、完整流接收、原始候选保存和结果引用校验。文字差异及原件身份是确定性事实；规则对应、实际业务关联、接口配对、传播影响、归因及复核必要性交给模型基于整个输入分析。文本diff为空也不由平台跳过当前完整分析；模型可以据全文说明未变化及静态边界。

`service.enqueue/retry`标记FULL_INPUT，`execution`直接复用公共 `responses.analyze → _model_response → send_response`，完整传入原根 `input_snapshot` 与全部固定原附件。没有调用batch_planning，不构造子输入，不拿各批结果替代全文。模型等待仍显式None，HTTP/流失败不自动重发收费请求，最终结果继续严格根契约与原件引用校验，入库/人工处理边界不变。

公共传输层保留既有无损相同长正文引用与连续input_text装配：它们属于同一次HTTP请求，完整展开和无分隔拼接后等于原根input，不是多个AI调用。它们不提供持久模型记忆，不扩大总上下文，也不保证模型一定接受约49.6MB请求。平台不把改成单次宣称为此前400/504已修复；上游不能接收时明确保存失败，由人工决定下一步，不静默缩范围、截断或自动分批。

历史V1/V2计划、Skill、原始候选、已校验成果及人工处理留在原记录。页面仅显示“历史分批进度”，移除继续分批开始按钮；旧start请求返回change_full_input_required。旧PREPARED/失败/取消及部分失败记录可以人工点击“完整输入重新分析（1次调用）”，新建retry_of记录，完整根输入仅按既定更新request_id，归档previous_batch_execution含原计划和处理审计，不复用旧批报告/人工确认冒充新的整体分析。重试仍使用重试者当前个人配置与授权，原Skill快照不替换；平台附加简短阶段说明消除旧Skill中的分批歧义。

当前Skill1.0.4，最终CHANGE_IMPACT契约仍2，无INTEGRATION/reconciliations包装。旧分批模块保留历史解释、已有任务兼容与免费候选重校验用途，不参与新FULL_INPUT请求。原文件单项约束、凭据安全、项目权限、来源/哈希/引用校验保持，无新表/字段/迁移/依赖/Worker。

验证采用完整输入整对象比较：最终模型请求的用户JSON在无损引用展开、连续文本重组后，必须逐项等于固定根输入，包括全部snapshot/unit/segment顺序、文字/行号/哈希/版本、比较对/scope/mapping/diff、targets/focus、上下文、用例设计和历史处理。二进制附件单独比较原字节。合成HTTP测试断言一次POST、timeout=None、完整completed才交付。历史413离线保留两侧各3327单元、3327映射，重组哈希与原input一致，没有新增模型调用。见outputs/change-full-input-offline-413-20261026.json。

开发说明中的V1/V2批次数与费用是历史方案数据，不能继续作为当前新任务的执行计划。多次独立请求不能被称作等价的“分批传输完整上下文”；若后续需要改变执行方式，必须明确模型实际能看到的原文范围及上下文限制，不再由平台以更多静态规则替代分析。
