## 1. 定位及与已有模块的关系

变更分析回答：**本次实际改变了什么、影响哪些业务和实现、是否引入新问题、需要回归哪些场景。**

| 模块 | 主要问题 | 与变更分析的关系 |
| --- | --- | --- |
| 需求分析 | 当前需求/原型有哪些遗漏、歧义、冲突及不完善之处 | 提供固定原文、功能风险和人工确认；变更分析核对规则如何变化、旧风险是否仍适用 |
| 代码分析 | 指定代码是否存在Bug、需求偏差、前后端不一致 | 提供固定代码、发现和证据链；变更分析沿变化追踪影响，并核查问题归因 |
| 变更分析 | 新旧需求或代码的变化影响什么 | 保存新旧对照、影响、风险和回归建议，人工审阅后按需进入原模块继续工作 |

不强制先做需求分析或代码分析。已有报告可以帮助选范围、定位旧问题，但报告摘要不能代替原文和源码；也不能只比较两份报告的风险数量就认定修复或新增问题。

2026-10-08用户进一步明确原型变更需独立区分来源：同一菜单提供**需求变更、代码变更、原型变更**三种入口。原型变化仍按业务规则/功能影响分析；GitHub原型使用旧新固定提交/文件范围，原型链接使用已保存旧页面正文及新读取页面范围，不能把URL或目录哈希当作历史正文。首期一次记录选择一种主方式，其他内容作核对依据，避免把独立变化直接认定因果。

现状依据：正式 `/changes` 仍走待接入页面；总HTML及审阅副本仍以手动核销的静态代码变化示例为主。当前 `app.chat_worker` 已轮流处理需求分析、代码分析及两类对话；已有GitHub客户端提供固定读取白名单，尚无变更比较/PR读取操作。本方案不把这些建议能力写为已实现。

## 2. 两种分析入口与目标

### 2.1 需求变更

流程：选择旧资料基准 → 选择新资料及更新方式 → 确认资料对应与比较范围 → 可选代码/用例/历史分析 → 开始 → 审阅业务变化及影响。

| 输入 | 要求 |
| --- | --- |
| 旧基准 | 已有需求/原型固定文件版本，或已完成需求报告中实际保存的输入；允许多份资料，不设主需求必选 |
| 新资料 | 同范围的新固定资料内容；可以与旧资料是同一来源不同版本，也可人工配对新的来源 |
| 更新方式 | 每个资料对应组指定“完整替换”或“增量补充”，多组可采用不同方式 |
| 对应关系 | 明确哪些新资料替换/补充哪些旧资料；新旧页面名、功能名相同只作为匹配候选 |
| 可选依据 | 已完成需求分析的功能/风险/人工处理快照、指定当前代码快照、现有用例设计版本、可定位的已确认规则 |

分析目标：默认“业务变化与功能影响”；可勾选“代码实现跟进”“用例维护与回归建议”。缺少代码或用例时，仍可分析业务变化，但对应目标显示依据不足，不能写成无影响。

“代码实现跟进”要说明指定代码版本对哪些新版规则已有静态实现证据、哪些存在偏差、哪些无法证明。没有旧代码时能判断指定实现是否符合新规则，但不能证明开发人员何时改动或问题是否本次引入。代码未改也可以先分析需求变化及待改范围。

### 2.2 代码变更

流程：选择来源 → 固定每个仓库/目录的新旧版本 → 查看变更文件 → 勾选变更文件并按需补选依赖 → 可选业务及用例依据 → 开始 → 审阅变化、归因和回归范围。

默认提供变化识别、影响追踪和回归建议；代码风险检查复用已有三个目标：代码Bug、需求符合性、前后端一致性。

| 目标 | 输入门槛 |
| --- | --- |
| 变化与影响 | 至少一组可比较的新旧代码快照，含实际内容及可验证的文件存在性 |
| 代码Bug | 可用单端代码；定位到执行路径和变更位置，不对未读文件猜测 |
| 需求符合性 | 实际可读固定版本需求/原型依据；该目标缺依据时保留不足说明，其他可执行目标按现有规则处理 |
| 前后端一致性 | 必须实际选取 BACKEND 和 WEB/FLUTTER 的目标侧代码，缺任一端拦截整次创建；原文、接口描述和旧版一端不能替代目标侧代码 |

单端发生变化时，可补选另一端未改变的目标侧文件进行一致性检查；要判断“本次引入”，还需相应旧版配对证据。两端均已读取也不代表接口已匹配。

GitHub和本地沿用代码分析的同次单一来源方式，支持同方式多个仓库/目录；每个来源分别比较，不跨仓库比较提交。BACKEND/WEB/FLUTTER类型从项目登记读取，不信任模型或上传文件自行声明。

## 3. 新旧版本、范围及差异规则

### 3.1 需求与原型

- **完整替换**：仅在明确替换的同一比较范围内识别新增、修改、删除。旧内容确实不在完整新范围内，才可提出删除；未选页面、读取失败、解析不完整不能充当删除依据。
- **增量补充**：有效新范围为旧基准加本次补充。补充未提到的旧规则保留；冲突须列出双方原文。只有明确且可定位的取消规则才能提出删除，不能把一份补充文件当作整份新需求。
- 2026-10-08用户明确：未更改规则不单独列为变化项，也不计入变化数量。增量继承关系只在固定比较范围中汇总说明；若旧规则或场景受本次变化影响，可在影响分析/回归建议中按实际关联引用，不能因为未变化就排除必要回归。
- 对比区分业务规则变化、仅措辞/格式调整、拆分/合并、冲突及无法确定。名称/章节变化不直接认定功能新增删除。
- 资料配对由用户核对，AI可提出功能或规则对应候选；一对多/多对一保留映射。报告内function_key不作为全项目稳定业务编号。
- 2026-10-08用户确认新建交互：同一资料仅勾选一次，在同一项选择旧基准/新目标，默认上一版→最新版；缺旧版本留空、相同版本拦截。两份文件的增量补充使用独立配对，标明旧基准文件＋新版补充文件，不混入同资料版本选择。
- 变更后原文仍有歧义时，先指出需产品确认的规则；AI建议不能变为已确认新要求。

### 3.2 GitHub代码

- 分支/Tag/PR是版本选择入口，报告保存最终完整提交SHA、仓库、文件blob标识、内容哈希和实际选定范围。
- 普通版本比较明确选择两个提交；PR须明确“共同祖先到PR目标”或“指定基准到目标”，显示实际SHA。不能混用共同祖先和基准分支最新提交。
- PR/比较读取需在既有客户端中新增固定只读操作及校验，不能接收任意URL或开放任意Git命令。首期可先做双提交；PR快捷入口可后续接入，不影响比较结论结构。
- 文件树展示两侧路径并集与变化标识，默认勾选可读变更文件；允许取消部分文件、补选上下游文件，显式显示未选及未读范围。选择目录的两侧比较范围一致。
- 原文读取失败、文件未选择、权限变化、敏感文件排除和二进制不可解析，各自说明；只有已核实某侧不存在才视为新增/删除，不能用空字符串伪造缺失内容。
- 重命名有可靠来源或用户确认映射时单列；仅相似内容标为候选，不能据此证明业务迁移。纯重命名不算新业务。
- 系统从固定内容产生可重复的文本差异及位置，再由AI解释业务含义；不让AI编造diff。哈希相同即文本未变，但被调用逻辑变化仍可能影响该文件行为。

### 3.3 本地代码和链接

- 本地选择同一已登记来源的两次已有浏览器快照，或“已有快照 → 用户主动读取最新”；保留序号、读取时间、范围、文件哈希和正文。无旧内容时不能创建代码变更任务，可返回代码分析审查现状。
- “纳入/移出读取范围”与磁盘新增/删除分开；读取跳过或失败不认定删除。目录读取不是文件系统原子快照，两次读取间的中间编辑不在证据范围内。
- 继续由来源拥有者在浏览器授权并提交所选两侧文本，不让后端读取本机路径。项目共享只针对已提交固定证据；项目成员不会因此得到目录句柄或代用他人电脑授权。
- 本地代码分析已有选定文本提交及个人AI调用规则可复用；本模块实现仍需正式授权，且不能自动同步全部浏览器历史。选择范围、项目保存及AI发送范围在开始前明确展示。
- 原型链接地址不等于历史版本。旧页面需来自已固定分析输入，新页面按现有受限读取器实际采集并固定；没有旧正文就提示缺基准，不能把同一URL读两遍冒充两个历史版本。只读HTML/说明的PARTIAL边界继续保留，不推定已看图片、执行脚本或批注已获人工确认。
- 建议沿用代码分析16MiB总输入上限，**合计两侧代码、资料及所选上下文**；双JSON导入每份上限同现有模块。超过明确要求缩小范围，不静默裁剪；此分析限额不改变项目设置中本地目录一般读取规则。

## 4. 结果组织与风险归因

每条完成记录保存五组相互引用的结果：

| 结果 | 必要内容 |
| --- | --- |
| 变化项 | 新旧对象、变化类型、原文/代码对照、业务含义、是否仅文字调整及覆盖缺口 |
| 功能/代码/用例影响 | 关联变化、目标固定引用、直接/间接、确定/可能/未知、传播链和建议动作 |
| 风险/代码发现 | 触发条件、预期及依据、当前行为、根因、严重程度、证据状态、变化归因与验证建议 |
| 历史问题复核 | 显式选择的旧风险/发现、旧依据、当前核查范围、仍存在/已有静态改善证据/无法核实/未检查 |
| 回归建议 | 优先级、功能、场景、关联用例及版本、推荐原因、前置条件/数据、操作及应核对结果 |

影响“确定”表示固定证据支持静态关联，不表示人工已接受或运行已验证。仅文件名/关键词相近只能给候选线索，不形成已确认影响链。

归因与严重程度、证据状态、人工处理分别保存：

| 归因 | 条件 |
| --- | --- |
| 本次引入 introduced | 同范围旧版证据支持旧行为不存在该问题，新版出现问题，并能定位相关变化及传播依据 |
| 原有问题 pre_existing | 旧版和新版证据均支持同一根因/触发路径；本次扩大可触达范围时另列“影响扩大” |
| 无法归因 unknown | 缺旧依赖、规则生效时间不明、版本不匹配或其他证据缺口；保留可疑问题但不算本次新增 |

需求改了而代码没改，可能构成“新版需求下的实现偏差”，不等于代码本次引入Bug。证据要标明旧/新规则适用范围与所核查代码版本。

历史风险未出现在新版报告里不算解决。“已有静态改善证据”只保存本次复核记录，不自动关闭旧风险，也不写测试通过；需要用户回到原模块按原处理规则记录结论。

同根因跨多个目标/变化项只保存一条发现，目标视图沿用代码分析的Bug执行路径、需求实现对照、接口字段对照；严重程度及计数不重复。不同记录不按同名自动合并。

## 5. 与需求、代码和用例的关联

### 5.1 显式选择并固定

新建时可带入当前项目内已完成的需求报告、代码报告及具体问题。保存模块、报告ID、对象key、输入摘要、处理修订号、操作者和当时处理结论。聊天原文和其他会话历史默认不进入分析；需求待核对警示随选中引用携带。

系统可沿所选报告定位已有固定证据，展示待选文件/资料候选。原始输入不包含的依赖只列待补范围，由用户再次选择，不自动扫全库。历史代码提交与当前提交不同须并排显示，旧发现的代码不能冒充当前实现。

用例引用采用内部case_id和实际设计版本，保存分析时设计字段及库修订号；展示编号可能重复，不能用于身份匹配。没有需求—用例现成关联时，仅输出带依据的关联候选，不假造已建立映射。用例未提供不算零条或无影响。

### 5.2 回归建议与用例动作分开

对已选用例给 KEEP、UPDATE、RETIRE；未有用例的场景给 ADD_SCENARIO。KEEP是保留设计，不表示无需回归。回归优先级另按变化直接性、业务影响、共享路径及证据缺口说明原因。

UPDATE说明应改字段/预期及所依据新版规则；RETIRE只提出停用建议。现有用例管理没有独立设计停用能力，不能借用“废弃”测试结果或逻辑删除代替停用。

首期保存建议、完整导出及跳到用例详情，允许用户按既有用例编辑流程处理。建议本身不修改用例、不继承旧版通过结果。后续用例生成UPDATE和共用人工应用获准后再带入固定变化引用；应用前核查当前设计版本，保留人工修改及测试历史。

“继续需求分析/代码复核”仅打开原模块入口并预填可识别的固定范围；用户核对后明确发起，才建立新任务和付费调用。不用跳转自动运行另一分析，也不假装尚未开发的用例生成入口可用。

## 6. 页面与交互建议

### 6.1 主页面

保留现有“变更分析”菜单名称、位置和分组。建议参考当前代码分析的三栏：

- 顶部：新建变更分析、导入分析结果、历史对话。
- 左栏：分析记录，显示需求/代码方式、基准→目标、时间/发起人、任务状态；搜索、分批加载和当前记录高亮。
- 中栏：当前记录概览及“变化项 / 影响与风险 / 回归建议”三个页签；每页10条。筛选按功能、变化类型、归因、等级和处理状态，各页签仅提供适用字段。
- 右栏：固定新旧范围、更新方式、资料配对、所选代码/用例/历史引用、目标处理情况及缺失证据；打开固定版本对照，不用资料页最新内容替换依据。

推荐默认按单条变更记录展示，避免不同基准的结果混成同一次变化。与OTHER_ANALYSIS_DESIGN早期“累计区＋左侧功能范围”建议相比，本稿改为代码分析式记录导航；这是待用户审阅的页面差异，原型未改。跨记录汇总可后续增加显式选择，不强行合并同名功能。

概览分开统计业务变化、仅文本调整、直接/可能影响、本次引入/原有/未知风险和建议回归场景。排队、失败、取消、尚未检查都不表示零风险；完成也不意味着所有目标都有充分证据。

### 6.2 新建与导入

新建弹窗：名称 → 变更方式 → 比较目标/更新方式 → 新旧版本与范围 → 补充依据 → 资料/文件对应及门槛确认 → 补充关注点 → 本人AI配置与开始。

版本/来源方式切换使该来源旧文件选择失效，其他来源选择保留；配对和对应关系重新核对。无差异可只读展示比较结果，不创建付费任务；若用户需要检查依赖变化，须明确补选实际变化依据。

导入弹窗复用两份原始JSON及来源绑定模式，预览新旧版本、方式、范围及结果摘要；后端通过后才入库。缺少原始新旧快照不能由一份Markdown报告补造。输入内代码可属于用户提供快照，必须标注未与真实仓库自动比对。

### 6.3 详情与人工处理

详情按“业务说明 → 新旧证据 → 影响链/代码目标视图 → 归因依据与缺口 → 维护/回归建议 → 人工处理”展开。代码按文件节点展示路径、两侧行号、片段和缺失依赖，不固定补出无证据的页面展示节点。

影响/风险可按代码分析既有语义设待处理、已确认、已处理、误报、需补充证据；回归建议独立设待审阅、采纳、暂缓、不采纳。非默认状态需说明，revision保护并发，保存处理历史；采纳回归建议只确认范围，不表示已执行。

变化事实与原始AI报告不可被人工处理覆写；误判通过说明和审计保留。来源问题当前处理状态发生变化时可查看原模块最新状态，同时保留本次引用时快照，不静默刷新分析上下文。

### 6.4 独立变更对话

按变更记录隔离独立对话历史，详情追问携带变化/影响/风险/回归项引用，继续同一记录对话。上下文仅取该记录固定双版本、结果、处理快照、明确带入的跨模块引用及本对话已完成消息。

发送使用提问者个人AI；一条记录仅一轮活跃对话，支持幂等与发起人取消。回答只保存为消息，不自动添加发现、修改用例、关闭旧风险或扩读资料。首期不增加附件、功能子会话或从聊天自动新增结构化问题。

页面及控件复用Form、FormSelect/Select、FilePicker、CaseDialog和既有主题样式，覆盖键盘、焦点、长路径、窄屏及弹层裁剪。原型阶段直接更新总HTML `#changes`及审阅副本，不交付孤立页面。

## 7. Skill、契约和校验建议

沿用双文件：调用方先保存input.json，AI仅返回结构化report.json。新模块独立采用 CHANGE_IMPACT 契约，不改需求v3或代码v2字段；2026-10-10已按设计授权创建`skill/change-impact/`草案，精确字段见[contract.md](../skill/change-impact/contract.md)，正式接入另行推进。

| 输入字段组 | 含义 |
| --- | --- |
| 身份与版本 | contract_version、analysis_type、request_id、project_id、任务revision、mode |
| comparison_pairs | 来源对应、新旧固定版本、范围、存在/不存在/未读状态、更新方式及diff位置 |
| before_materials / after_materials | 需求方式的固定旧资料、新资料及有效合并范围；原文不被合并结果覆盖 |
| before_code / after_code / diff | 代码方式的两侧正文、来源角色、文件/片段标识、哈希及系统计算差异 |
| targets / context | 目标、已选当前代码/资料/用例、已确认规则、历史分析及处理快照 |
| focus / limitations | 补充关注点、排除及范围缺口 |

| 输出字段组 | 含义 |
| --- | --- |
| changes | 稳定的本报告变化key、新旧证据、业务差异/文字差异及对应关系 |
| function_impacts / code_impacts / case_impacts | change_keys、目标引用、影响、直接性、静态确定性、证据及建议动作 |
| risks | 代码分析式目标视图及证据链，增加归因、归因依据、历史发现引用和影响扩大说明 |
| historical_reviews | 对显式选定旧问题的本次复核结果，不携带修改旧状态指令 |
| regression_scope | 场景、优先级、原因、用例版本、前置数据、操作和应核对结果；同一回归场景可关联多个变化 |
| coverage / missing_dependencies / summary / limitations | 每个比较组两侧的实际读取与检查范围、各目标完成程度、缺口和结论边界 |

新增/删除证据允许一侧为“经清单核实不存在”；不能用未读/未选代表不存在。所有证据带BEFORE/AFTER/CONTEXT侧别，行号分别对照对应版本，严禁跨侧摘录混用。

建议继承代码分析的源码严格校验：对象/引用/原文坐标/哈希及目标门槛错误阻断正式报告，保留原候选。需求语义偏差参考现有需求分析显式待核对机制：形状、项目和引用编号仍硬校验，语义不充分的业务判断携带review_warnings并降为未知/待核对，不能继续作为确定归因或确定影响依据；人工双JSON导入保持严格。该新模块校验策略属于本稿建议，待正式契约落实。

归因introduced缺少可核验新旧证据时必须拒绝该确定标签或降为unknown并留下警示；不能为凑出完整结果编造旧版正确行为。结构正确、源码摘录匹配也只证明引用有效，不证明推理正确或测试通过。

完整AI候选在校验前原子保存，失败不冒充报告；原发起人可无AI手动重校验已保存候选，不能借重校验替换输入。相同项目输入/结果重复导入返回原记录，保留人工处理；不同结果另建记录。

## 8. 后台、权限和实现归属

沿用个人AI、项目共享、离开继续、发起人取消、失败人工重试、重试者本人配置等已确认原则。执行前、外部请求返回后、报告保存前复核账号、项目、来源及配置版本；网络等待不持有事务。取消/撤权/配置变化后的返回不能保存为成功。重启中断不自动重放可能计费的任务。

输入准备完整后即固定，重试复用同一两侧快照并新建任务/request_id；换版本或补范围属于新分析，不是重试。未完整固定的输入不能混入稍后取得的最新一侧，应明确失败并重新确认比较对。

正式实现建议放 `backend/app/modules/change_analysis/`，按实际职责拆router/schemas/service、sources/diff/contract、execution/chat/export。数据建议以变更任务记录保存状态、固定input/report、来源绑定、Skill全文/摘要、个人AI配置版本和安全诊断；独立保存人工处理及对话历史，原始结果不可变。按既有模式设计必要表/字段，不预建通用依赖图或知识库；DDL及中文COMMENT在正式开发时审查并用Alembic落库。

依赖方向：change_analysis → 项目鉴权、资料、需求/代码分析公开只读服务、用例版本读取、个人AI及integrations；这些模块不反向依赖change_analysis。现有代码sources/contracts中只有确实复用的读取或证据能力才提取，不能把整个代码任务执行器套在变更任务上，也不能通过导入其他模块router复用。

Worker继续使用 `app.chat_worker`，增加明确的变更分析/对话领取与恢复函数，并按现有方式轮流领取；不恢复analysis_worker、不新增Redis或通用Agent。单执行进程的长模型调用仍会延后其他任务，轮询不等于并行执行；多进程调度不在首期建议范围。

拟议API基路径 `/api/projects/{project_id}/change-analysis`：记录列表/详情/options、只读比较准备、新建/import、cancel/retry/revalidate、handling、export/candidate和独立chat。它们仅为接口设计清单，当前不存在，不对外承诺可调用。

前端仅在frontend，业务API复用api/http；后端路由不写SQL或网络；GitHub扩展仍是固定GET白名单，无Git写入、代码执行、自动测试、推送或部署。

## 9. 实施顺序与验收

建议先确认本稿的比较规则、页面结构和首期能力，再进行：

1. 更新总HTML和审阅副本：两种入口、新旧配对、三类结果、详情、处理及历史对话，用合成数据明确演示完整/部分/失败状态。
2. 落实change-impact Skill、独立契约及双侧完整合成样例；重点验证归因、范围变化、增量补充、跨模块引用反例，不调用真实模型冒充质量评测。
3. 实现双JSON导入、固定记录、只读跨模块引用、处理与完整导出，先验证无AI闭环。
4. 接入GitHub双提交/本地双快照和需求固定双版本，复用Worker真实个人AI任务、候选及独立对话；PR快捷选择可随后补充。
5. 用例建议先保留人工维护；共用用例草案应用、设计停用及跨模块自动预填能力随相应模块授权接入，不把它们作为首期上线必备。

验收至少覆盖：

| 场景 | 应有行为 |
| --- | --- |
| 完整替换仅选择部分新版章节 | 未比较的旧规则不判删除；覆盖明确部分 |
| 增量文件未提到旧规则 | 旧规则仍保留；冲突双方并列待确认 |
| 原型链接没有旧内容 | 拦截需求变更，不把同URL当两个历史版本 |
| 两侧文本相同 | 展示无文本变化，不自动付费；未读依赖不算无影响 |
| 本地移出范围/读取失败 | 不算文件删除；无基准不能代码变更 |
| 多仓库只有后端改动 | 各仓库比较对独立；另一端可作为未变上下文 |
| 选择一致性缺目标侧一端 | 前后端同时强制拦截整次创建 |
| 旧报告发现未在新报告出现 | 保留旧状态，标本次未检查或显式复核结论 |
| 旧版已有Bug但新增入口可触达 | 原有问题＋影响扩大，不一律归为本次引入 |
| 需求升级而代码未变 | 标新版规则下偏差，代码归因不虚构 |
| 新旧摘录或行号混用 | 拒绝正式确定证据，保存候选供排查 |
| 需求语义待核对被引用 | 警示进入列表/详情/导出/对话，不作为确定依据 |
| 用例展示编号重复或已被人工修改 | 按内部ID/设计版本准确引用，建议不覆盖当前设计 |
| 建议停用/采纳回归 | 不删除用例、不修改测试结果、不写已执行 |
| 无用例或仅提供部分用例 | 明确未检查/局部范围，不声称全库无影响 |
| 取消/撤权/配置改变/Worker重启 | 不保存伪成功、不自动付费重试 |
| 重复导入/处理并发冲突 | 幂等返回原记录，revision拒绝过期处理 |
| 追问、切记录/项目和跨页导出 | 上下文不串，聊天不改业务，导出包含全记录及来源警示 |

前端改动运行请求回归、UI规范、check/build及原型检查，并完成键盘/焦点/窄屏视觉核对；后端运行相关测试、Ruff及架构检查。数据库变更必须检查中文COMMENT、实际迁移及Alembic一致性。真实外部不可用时说明模拟边界，模型效果另用真实授权样本评测。

## 10. 首期推荐范围与待审阅选择

建议首期包含两类变更、双版本固定、业务变化与影响、代码三目标联动、历史问题显式复核、回归建议、配对导入、人工处理、完整导出及独立记录对话。

需要在原型及正式开发前核对的新增选择为：单记录三栏与三个结果页签；逐资料组完整替换/增量补充；本模块需求语义警示与源码严格校验；PR快捷入口后置；用例只给建议和人工维护、不提前实现应用/停用。本方案采用这些默认建议，尚不将其记为用户已确认决定。

## 11. 场景示例（合成，非真实项目结果）

代码变化：旧扫码入口包含门店归属校验，新版增加手动输入核销入口；固定源码显示新入口仅校验订单状态后完成核销。

- 变化项：新增手动输入入口，保存新增位置及旧版入口证据。
- 功能影响：人工输入的订单核销路径；若完整旧范围证明此前没有该入口且新路径绕过校验，可标本次引入。旧公共服务本就缺校验且旧入口也可绕过时，应标原有问题/影响扩大。
- 代码对照：客户端请求 → 接口路由 → 服务校验 → 完成动作，仅列已读取节点；缺路由或服务文件时不能拼成确定链路。
- 回归建议：本门店有效订单通过、其他门店拒绝、无效码、已核销订单、原扫码入口、共用服务其他调用方；给出每项前置数据和应核对响应/数据状态，不声称实际运行通过。
- 已有用例可保留扫码越权用例并纳入回归，建议新增手动入口越权场景；由用户维护后再执行，不自动生成测试结果。

需求变化：补充说明“手动输入也必须核对门店归属”。采用增量补充时，未提及的原扫码规则继续保留；指定代码仍缺检查时输出新版需求偏差。旧规则此前是否已要求手动入口、旧代码是否有同一缺陷须分别核实，不能把需求补明确写为代码新Bug。
