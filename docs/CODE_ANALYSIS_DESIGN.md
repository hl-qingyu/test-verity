## 1. 目标与边界

代码分析回答三类问题：

1. 当前实现有没有可定位的 Bug 或安全/数据风险。
2. 当前实现是否偏离已经固定的需求、原型或已确认业务规则。
3. 前端、接口、后端、数据处理和最终展示之间是否存在取值或语义不一致。

代码分析是静态证据审查。它可以提出运行验证建议，但不能把静态结论说成测试环境已复现，也不能自动修改代码、执行脚本、运行 Git 命令或写入远端。

首期建议先支持 **GitHub 项目已关联仓库的固定提交和选定文件**。本地代码目前只在浏览器中读取并保存在本地，尚未授权把源码上传到后端或发送给个人 AI；在该边界确认前，本地代码只能显示为“可选来源，尚未接入代码分析”。

代码分析不强制先完成需求分析。没有需求资料时仍可做 Bug 检查，但报告必须标明“未核对需求”；需求符合性和前后端一致性缺少对应输入时，输出证据不足，不猜测结论。

## 2. 页面与记录关系

沿用需求分析页面结构，菜单继续使用现有“代码分析”入口，不增加报告管理菜单。

### 2.0 前端界面实现约束

正式前端必须按已确认总HTML原型核对布局、间距、颜色、状态和交互，不得以能工作的原生控件替代原型控件。代码分析新建弹窗复用平台的 `CaseDialog`、`Form`、`FormSelect` 和 `requirement-ui` 样式；来源、仓库、连接和固定版本使用主题下拉，资料与代码文件使用主题复选项，文件树工具栏统一提供全选、清空和已选数量。控件保留原生语义、键盘、焦点和禁用状态，但可见外观必须使用共享样式。新增代码分析控件先复用已有样式，只有原型确有差异时才增加模块级样式；不得直接引入原生可见 `select`、浏览器 `alert/confirm/prompt` 或未主题化弹窗。

### 2.1 主页面

顶部操作沿用“新建代码分析”“历史对话”。左侧为分析记录，中间显示所选记录的发现列表（每页10条），右侧为本记录固定版本与文件范围，不增加按功能分类的导航。概览展示高风险、证据不足和当前记录发现数量；导出按所选记录包含所有页。筛选仍按原型的演示边界，不因本轮改动新增业务能力。

卡片分别展示问题类型、严重程度（高/中/低/待评估）、证据状态（静态证据充分/证据不足）和人工处理状态。高风险可以证据不足，低风险也可以证据充分；“已处理”不改变证据状态或代表运行验证通过。

### 2.2 发现详情

详情按以下顺序展示：

1. 标题、问题类型、严重程度、证据状态、静态分析未运行验证、人工处理状态。
2. 问题说明：触发条件、预期行为及判断依据、实际行为。
3. 调用链与证据：按实际提供的节点展示文件位置、观察和可展开的固定代码片段；缺失环节单独标识，不强行拼成完整链路。前后端位置继续保留。
4. 影响与建议：影响范围、修复建议、验证建议；证据不足时展示待补充证据清单。
5. 人工处理：沿用待处理、已确认、已处理、误报、需补充证据及处理说明。

2026-09-20用户确认移除无代码证据的固定“页面展示”节点；后续明确前端展示逻辑与后端调用链均可在代码支持时展示。允许核查条件渲染、状态赋值和文案映射，不要求运行截图，不把静态推导写成页面实际运行结果。是否展示某一节点由当前目标及证据决定，不按前后端完整模板补空位。

有具体可疑路径但缺少关键证据的条目仍作为“证据不足”发现展示，不算已确认Bug；仅缺少资料而没有问题线索的情况应进入范围说明。补充清单只提出建议，不新增自动读取、上传或复核任务入口。本轮修改总HTML与审阅副本，并同步原型Markdown导出；正式系统尚未接入这些新增展示字段。

主卡片只显示摘要。源码片段、差异和长调用链在详情中按文件展开，避免代码铺满主页面。用户打开的代码片段只来自本次固定输入，显示仓库、提交、路径和行号；不存在可靠位置时显示证据不足。

### 2.3 独立代码分析对话页

代码分析使用独立页面、独立路由、独立 API 和独立数据范围。只复用平台级视觉组件和基础交互，不直接套用需求分析对话页面，也不显示“需求分析对话”“需求风险”或需求报告专属操作。

页面布局可以保持同样的三栏密度，但内容不同：

- **左侧：代码分析导航**：当前代码分析对话、按功能切换的代码对话、代码分析历史、创建新的代码分析；历史只列代码分析记录。
- **中间：代码审查对话**：显示当前代码分析名称、固定提交/快照、检查目标；输入提示围绕调用链、字段映射、异常路径和证据补充，不默认提示需求风险问题。
- **右侧：代码上下文**：仓库/本地快照、提交或快照号、选定文件和目录、读取状态、当前功能、关联代码发现。文件链接打开固定版本位置；不展开整个仓库源码。

代码发现追问进入所属功能的代码分析对话，携带代码分析 ID、发现 key、提交/快照和证据引用，不创建发现专属会话。没有需求资料时右侧明确显示“未核对需求”，不能把需求分析页面的上下文占位复制过来。

普通聊天只保存代码分析消息。AI 回复中的新问题只能通过“添加为代码发现”进入人工确认表单，确认后保存为待处理代码发现；聊天不能直接改变发现状态、代码或需求资料。

### 2.4 首期只做独立代码分析对话

需求分析和代码分析可以复用消息队列、个人 AI 配置、历史分页和引用组件，但代码分析首期只建立自己的页面和对话范围：固定代码快照、代码报告、发现处理和本代码分析对话历史。需求报告、需求聊天、用例聊天和其他模块历史不自动进入代码分析。

每轮消息保存 `context_refs`，至少记录代码分析 ID、报告修订号、代码提交/快照、功能 key、发现 key 和证据 key。右侧引用只按代码来源分组，显示仓库、提交、路径、行号和报告发现；没有需求依据时明确显示“未核对需求”。

代码分析对话只产生带代码来源的 AI 回答。回答不能自动修改发现、代码、需求资料或处理状态；需要正式变更时回到代码发现详情的人工处理入口。每轮仍保存模型、个人 AI 配置版本、推理档位、提示/Skill 摘要、上下文版本和完成时间，明确 AI 回答可能因上下文、代码版本和随机性不同而不同。

需求与代码的联合复核、跨模块上下文选择、冲突对照和人工结论暂缓设计，不进入首期代码分析页面、接口或数据库。

## 3. 新建分析流程

最新原型弹窗顺序：分析名称 → 检查目标 → 代码来源与范围（含类型与固定版本）→ 需求/原型依据 → 本次检查范围确认 → 补充关注点 → 执行配置。未新增用例资料入口。需求符合性至少需要一份满足固定版本条件的依据，其他目标可选补充资料。

范围确认逐项目标提示输入条件和缺口，切换目标不清空已选代码/资料。最新规则：勾选前后端一致性时，实际选定文件必须同时来自BACKEND及WEB/FLUTTER；缺少任一端提示并拦截整个任务，即使其他目标满足条件也不能创建。其他目标沿用部分依据不足提示，全部不可执行时阻止创建。原型只保存待接入范围，不读取真实代码、不调用AI、不产生分析发现。仓库类型来自来源登记；GitHub与本地均适用，同一来源方式支持多个仓库/本地目录。来源切换和版本切换沿用原有文件选择失效规则。

### 3.1 检查目标

可多选：

- 代码 Bug
- 需求符合性
- 前后端一致性

选择“代码 Bug”时需求可为空。选择“需求符合性”时至少需要一份实际可读取的需求或原型依据；选择“前后端一致性”时必须同时选择后端与前端/移动端代码文件，缺少一端直接提示拦截，接口协议不能代替一端实现。两端都有文件也不代表已核实接口关联，后续分析仍需说明具体证据缺口。

### 3.2 GitHub 来源

仅使用当前用户有权读取、且已经关联到项目的仓库：

1. 选择一个或多个仓库。
2. 固定具体提交 SHA；分支或 Tag 只作为选择入口，不能作为报告版本。
3. 展示完整支持文件清单，支持路径搜索、目录选择、全选、清空和逐文件选择。
4. 将仓库、提交、路径、文件 SHA、大小和实际读取状态保存为输入快照。
5. 读取范围外的依赖只记录为缺失依赖，不自动扩大范围。

读取只走现有 GitHub 固定 GET 白名单。平台不 clone 到任意目录，不提供任意 Git 命令，不 push、修改文件、创建或合并 PR。

### 3.3 本地代码来源

本地来源沿用 LocalCode 的目录授权和浏览器快照，但正式代码分析前必须再次确认：

- 哪些文件内容可以上传到平台后端；
- 是否允许发送给当前用户个人 AI 服务；
- 后端保存多久、谁可以查看和删除；
- 凭据、私钥、环境文件、依赖和构建产物如何排除；
- 浏览器快照与后台分析使用的服务器快照如何关联。

在这些决定确认前，不允许后台任务读取浏览器 IndexedDB，也不把本地代码显示为已固定的 AI 输入。

### 3.4 需求、原型和用例依据

需求、原型和用例是可选补充，但按检查目标校验：

- 需求符合性：固定版本需求/原型内容；
- 前后端一致性：固定接口契约、前端和后端代码；
- 业务回归提示：可带入已完成需求风险、已确认结论和用例版本作为线索。

风险报告、聊天结论和用例编号不能替代原始需求或代码证据。跨模块带入必须由用户选择并保存来源 ID、版本和引用位置。

## 4. 输入契约建议

代码分析单独使用 `CODE_REVIEW` 契约，不把代码字段塞入需求风险 v3。核心输入如下：

```json
{
  "contract_version": 1,
  "analysis_type": "CODE_REVIEW",
  "request_id": "uuid",
  "project_id": 1,
  "revision": 12,
  "focus": "重点检查订单核销的前后端状态一致性",
  "targets": ["BUG", "REQUIREMENT_DEVIATION", "FRONTEND_BACKEND_MISMATCH"],
  "code": [
    {
      "source_id": "C1",
      "kind": "GITHUB",
      "repository": "team/app",
      "commit": "40位SHA",
      "paths": ["frontend/lib/verify.dart", "backend/src/VerifyService.java"],
      "files": [
        {
          "path": "frontend/lib/verify.dart",
          "sha": "文件SHA",
          "text": "固定文件内容",
          "read_state": "READABLE",
          "segments": [{"segment_id": "f1", "location": "L20-L48", "text": "片段"}]
        }
      ]
    }
  ],
  "materials": [],
  "functions": [],
  "decisions": [],
  "cases": [],
  "related_risks": [],
  "runtime_evidence": [],
  "limitations": []
}
```

`runtime_evidence` 只能来自用户提供的日志、接口样本、测试结果及其环境/时间/版本，不由模型生成。目录和文件名可以作为范围索引，但没有文件正文就不能作为实现证据。

## 5. 输出契约建议

```json
{
  "contract_version": 1,
  "analysis_type": "CODE_REVIEW",
  "request_id": "uuid",
  "outcome": "COMPLETE",
  "summary": {
    "assessment": "NEEDS_CLARIFICATION",
    "conclusion": "已检查固定范围，发现一处前后端字段不一致。",
    "priority_finding_keys": ["F1"]
  },
  "functions": [],
  "findings": [
    {
      "key": "F1",
      "type": "FRONTEND_BACKEND_MISMATCH",
      "severity": "HIGH",
      "severity_reason": "完成态字段在前端映射中丢失。",
      "certainty": "CONFIRMED",
      "verification_state": "STATIC_ONLY",
      "function_refs": ["FUNC1"],
      "title": "前后端完成状态字段名称不一致",
      "trigger": "用户打开已完成订单详情",
      "expected": "页面显示已完成状态",
      "actual": "前端读取另一个字段并回退到待处理",
      "impact": "用户看到错误状态，可能重复操作",
      "evidence_refs": ["E1", "E2"],
      "call_chain_refs": ["CHAIN1"],
      "fix_suggestion": "统一序列化字段或前端读取路径",
      "verification_suggestion": "补充接口字段和页面状态回归",
      "handling_required": true
    }
  ],
  "call_chains": [],
  "missing_dependencies": [],
  "suggested_checks": [],
  "coverage": [],
  "limitations": []
}
```

每条发现必须能够回溯到本次输入的 `evidence_refs`。`certainty` 与 `verification_state` 分开：静态证据充分不等于运行验证通过；`PRE_EXISTING`、`INTRODUCED` 等变更归因不放入本契约，由变更分析负责。

### 5.1 证据对象

代码证据至少包含：`source_id`、仓库或本地快照、提交/快照 ID、文件路径、起止行、摘录和观察。需求/原型证据沿用资料片段结构，用例证据包含内部 `case_id`、设计 `version`、字段和摘录。不能仅凭文件名、风险编号或展示用例编号建立证据。

### 5.2 调用链对象

每个调用链节点包含：顺序、层级、文件路径、行号、符号/方法名、输入输出字段、已确认事实和未知环节。链条可以中断，但必须写出中断位置及影响；不能用模型猜测补齐后端、数据库或前端展示。

## 6. 校验、保存和人工处理

Worker 在发送前保存固定输入快照和 Skill/契约版本摘要；接收完整 Responses 完成事件后按契约校验，再原子保存分析记录、报告、代码绑定、资料绑定和处理记录。JSON 不完整、额外字段、未授权范围、证据定位不匹配或引用未读文件时，任务失败且不生成正常报告。

发现处理沿用需求分析状态：待确认、已确认待补充、已解决、不适用。静态发现另显示验证状态：未验证、已有运行证据。非待确认必须填写人工结论；“已解决”不等于代码已修复或测试通过。

结果只读共享。人工处理、复核结论和新一轮代码分析分别保存，不覆盖原始代码快照、模型结果或旧发现。新版本没有再次报告某问题，不自动关闭旧发现。

## 7. 后台、权限和安全

- 复用当前需求分析的独立 Worker、任务状态、请求 UUID、取消、失败人工重试和项目权限。
- 每次发起/重试使用当前操作者自己的 AI 配置，不使用平台密钥，不借用原发起人配置。
- 执行前后重新检查项目权限、仓库授权、提交仍可读取及代码来源版本。
- 外部 GitHub 读取前释放数据库事务，返回后重新检查权限和任务状态。
- 不执行代码、构建、测试、脚本、包管理器或模型返回的命令。
- 日志不写源码、完整提示词、密钥、完整响应或代码摘录。
- 代码快照按项目权限访问；本地源码的跨成员共享、删除和保留期限未确认前不得实现。
- 大范围代码不静默截断。超过模型容量时任务失败或要求用户缩小范围；不得自动拆分后宣称完成全库分析。

## 8. 任务与数据模型草案

不提前建表。正式开发获批后建议增加独立的代码分析任务和报告表，避免把异构结果塞进 `requirement_risk_analysis` 或 `requirement_risk_report`：

- `code_analysis_task`：项目、发起人、请求 UUID、目标、状态、固定输入、AI 配置版本、失败码、重试关系、报告 ID；
- `code_analysis_report`：契约版本、结果、摘要、代码来源绑定、需求/用例绑定、创建人、创建时间和修订号；
- `code_analysis_handling`：发现 key、状态、结论、操作者、时间、前后状态和修订号；
- 如确认保存服务器端代码，再增加受权限和保留策略约束的代码快照表/对象存储引用。

所有新增表、字段和迁移必须有中文数据库 COMMENT；报告与代码快照不可因重试覆盖，处理使用乐观锁，批量写入使用项目事务锁。

## 9. 分层调用链草案

```text
代码分析页 → codeAnalysisApi → 公共 HTTP → modules/code_analysis/router
→ code_analysis/service：项目权限、来源范围、仓库/提交校验、任务幂等
→ db：固定输入快照和任务
→ app.chat_worker：领取 code_analysis_task
→ integrations/github：固定 GET 读取选定提交文件
→ modules/code_analysis/execution：组装 input、读取 code-review Skill、调用个人 AI
→ code_analysis/schemas：校验报告和证据定位
→ code_analysis/service：保存报告、来源绑定和处理入口
→ 前端累计清单/详情/独立对话
```

服务不导入路由，路由不写 SQL 或外部请求，GitHub 客户端不依赖业务模块，前端只通过公共 HTTP。执行器不恢复旧 `analysis_worker`，但需要在现有 Worker 中按任务类型明确分支，避免需求分析任务和代码分析任务相互覆盖或长期饥饿。

## 10. 开发前必须确认

1. 首期是否只做 GitHub，还是同时允许本地代码上传到后端。
2. 本地源码发送到个人 AI 的授权范围、保存期限、删除人和项目成员可见性。
3. GitHub 支持的语言、文件大小、单任务文件数和排除目录；超过上游上下文时是失败还是用户拆分。
4. 是否允许用户提供运行日志、接口样本和测试结果作为证据；这些资料的敏感信息过滤规则。
5. 发现严重程度、静态置信度、处理状态和复核关联的最终枚举。
6. 代码分析结果是否允许被变更分析和用例分析主动带入，还是必须每次人工选择。

## 11. 验收场景

- 仅 Bug 检查没有需求资料时可以创建，但报告明确未核对需求。
- 选择需求符合性却缺少可读需求资料时阻止创建，或明确进入材料不足状态，不能假称完成。
- 勾选前后端一致性但仅有前端/移动端或仅有后端文件时，提示缺少哪一端并拦截创建；多选其他目标不绕过该限制，不伪造另一端链路。
- 固定提交后分支发生变化，已保存任务仍使用原提交；无权读取或提交不存在时失败。
- 选择范围外依赖只显示缺失依赖，不自动读取范围外文件。
- 凭据、`.env`、依赖和构建产物不会进入输入或日志。
- 无运行证据时发现显示 `STATIC_ONLY`，不能显示已复现或测试通过。
- 取消、断流、模型拒绝和报告校验失败不生成完成报告；用户重试后产生新任务，不覆盖旧记录。
- 两次分析出现相同问题时保留两个来源；新结果不自动关闭旧发现。
- 普通聊天不改变发现和处理；“添加为发现”必须经过人工表单和固定证据核对。
- 项目切换、成员权限变化和仓库授权撤销后，历史只按权限可见，后台执行拒绝失效授权。

## 12. 实施顺序

1. 先确认 GitHub 首期范围和代码外发/保存边界。
2. 建立 `skill/code-review/` 的 Skill、契约和完整合成 input/output，并通过结构/证据校验。
3. 复用需求分析任务状态、个人 AI 配置和 Worker，接入 GitHub 固定提交文件读取。
4. 先做只读报告、累计清单、详情和人工处理，再接入独立功能对话。
5. 最后评估本地代码来源、运行证据和变更分析联动，不提前建空表或空接口。

本方案不授权执行代码、Git 写操作、自动修复或默认把本地代码发送给 AI。所有新增业务实现仍需依据本方案重新确认字段、权限、接口、异常和验收标准。
