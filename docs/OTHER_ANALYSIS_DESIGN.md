## 2. 四个模块分别解决什么

| 模块 | 主要问题 | 主要结果 | 人工确认后的动作 |
| --- | --- | --- | --- |
| 用例生成 | 所选需求应该怎样测，需求更新后哪些用例需要维护 | 新增用例草案、字段修改、停用建议、保持不变、冲突与待澄清问题 | 选择并核对草案后新增用例或保存设计新版本 |
| 用例分析 | 现有用例是否符合需求，是否存在遗漏和设计问题 | 用例问题、缺失场景、需求待澄清问题、可选修改草案 | 记录处理结论；完整草案经单独确认后应用 |
| 代码分析 | 实现是否有Bug、是否偏离需求、前后端是否一致 | 功能发现、预期与实际、调用链、缺少的依据、建议验证 | 记录处理与复核，导出修改建议；不直接改代码 |
| 变更分析 | 新旧需求或代码差异会影响什么，哪些场景值得回归 | 业务变化、功能/代码/用例影响、风险归因、回归建议 | 确认影响范围，按需转用例维护或代码复核 |

四个模块可独立发起。不强制先完成需求分析，也不强制串成流水线。已有需求风险与人工处理结论可选入作为线索；用于判断的原始依据仍必须实际读取、固定版本并保留引用。

## 3. 统一页面与对话

### 3.1 分析主页面

沿用当前需求分析的布局与主题组件：

1. 顶部：新建分析会话、历史会话、导入分析结果。用例生成主按钮命名“新建生成会话”；模块标题沿用现有菜单。导入只在该模块输入/结果契约及校验完成后可用，不把需求v3导入复用为任意JSON入口。
2. 紧凑概览：已完成次数、功能数量、当前模块结果统计；正在处理和失败的分析另显示状态，不能算作零问题。
3. 分析记录折叠区：名称、范围及版本、时间/发起人、任务状态、结果数量、资料与结论、筛选本次、进入对话、取消/重试。变更分析额外显示基准→目标。
4. 左侧功能范围：累计功能项，附来源分析；同名功能不自动合并。无问题但已检查的功能仍显示。尚未识别功能时显示明确范围，而非造一个业务功能。
5. 右侧结果清单：结果种类、等级、处理或应用状态筛选，每页10条。卡片含问题/建议摘要、关联对象、来源、关键影响、追问、详情。
6. 清单导出位于概览操作区：按来源、功能、类型、状态组合导出全部匹配项，跨页生效，展示实际数量；空结果阻止导出。

累计的是各次分析的发现或建议，不代表当前系统去重后的缺陷数。不跨来源自动合并、覆盖或关闭；同一用例被多次建议修改时，必须在应用前识别冲突。

### 3.2 独立对话页面

各分析模块拥有自己的对话页面和语义。可以复用三栏布局、消息气泡、分页、弹窗和主题控件，但不能直接沿用需求分析页面的标题、字段、提示词、路由、API或上下文。代码分析详见[CODE_ANALYSIS_DESIGN.md](CODE_ANALYSIS_DESIGN.md)。

每个模块的左侧只列本模块分析与功能对话，中间显示本模块检查目标，右侧显示本模块固定依据、版本和结果引用；不把需求分析页面复制后仅替换标题。

- 对话按“项目＋模块＋分析记录＋功能”隔离；风险/问题追问进入所属功能对话，引用不是新建独立会话。需求、代码和用例可以复用同一聊天基础设施，但首期不自动共用历史；跨模块联合复核暂缓。
- 普通聊天只保存消息。跨模块参考必须由用户选入并固定当次引用，不自动拼接所有项目聊天。
- 回复可“添加为问题”；用例生成还可“添加为用例草案”。先打开主题表单，核对功能、证据和字段，确认后保存为待审阅；聊天语句不能直接改变用例或处理状态。
- 补充资料、会话附件、长历史整理的保留规则仍沿用需求分析的待定边界，不把这些能力假定为现成可复用。
- “当前资料已更新”只作提示；本次分析仍使用固定版本。正式复核新资料须显式建立新分析或新输入批次，不覆盖旧结果。
- 未来联合复核只产生带来源的对话回答，不直接合并或覆盖需求风险、代码发现和用例状态；本期不实现该入口。

### 3.3 状态必须分开

| 对象 | 建议状态 | 含义 |
| --- | --- | --- |
| 后台任务 | 排队中、分析中、已完成、失败、已取消 | 执行进度，不代表业务结论 |
| 分析完整性 | 完成、部分完成、材料不足 | 是否完成声明范围，不是质量评级 |
| 问题处理 | 待确认、已确认待补充、已解决、不适用 | 沿用需求分析；非待确认填写结论 |
| 用例建议 | 待审阅、已应用、已忽略 | 独立于问题处理；版本冲突阻止应用并要求重新核对 |
| 运行验证 | 未验证、已有运行证据 | 与静态发现分开；标记已解决不等于测试通过 |

初次结构化结果通过校验后保存为待审阅产物；“保存结果”不等于确认内容正确或自动应用。

## 4. 用例生成

### 4.1 新建与输入

弹窗顺序：会话名称 → 生成模式 → 需求/原型 → 功能范围 → 现有用例 → 分析目标 → 本人AI配置说明。

- 首次生成：需求或原型至少一项，覆盖全部所选范围或指定功能；可以没有现有用例。系统展示实际会用于判重的现有用例范围，不暗中读取全项目。
- 用例维护：当前需求/原型与已有用例固定版本必需；旧资料、历史设计及应用映射可选。导入/人工用例无生成记录也可维护，无历史时按现状核对且注明无法归因变化。
- 可选择已有需求分析记录带入资料及相关人工结论，仍可核对范围，不用风险清单代替完整需求。
- 原型不足以给出业务预期时，产出待澄清问题；不因必须生成用例而编造权限、数值和状态规则。

### 4.2 页面与结果

主标题“用例生成”，概览显示待审阅新增、修改、停用、冲突和已应用数量。右侧默认“全部建议”，可切换新增/修改/停用/保持不变/待澄清。没有实际变更的保持项不计待应用数量。

详情复用14列用例字段及既有编辑表单。修改建议显示“当前固定版本”和“建议版本”的字段差异、变更依据；停用建议显示原因与影响；冲突突出当前人工改动与模型建议差异。

14列沿用：序号、用例编号、功能模块、功能结构、用例类型、优先级、用例描述、验证用例子项、前置条件、操作步骤、预期结果、测试结果、测试人员、备注。数据准备/清理等详情字段复用现有定义，不新增另一套导出格式。多个步骤可对应场景级预期，不检查行数相等。

### 4.3 人工应用

1. 用户勾选草案，可先人工修订；模型原始建议和人工修改分别保留。
2. 显示将新增、修改、停用多少条，以及无法应用的冲突；默认不选停用建议。
3. 统一确认固定集合后逐条核对权限、目标/草稿版本、分类与复用/判重决定，每条独立事务。失败条目记录原因，继续下一条；成功项保留，失败项由人工核对后重新预览重试。任务级失权或存储不可用应暂停，不绕过权限。
4. 同场景优先建议关联已有用例；确认复用后结束候选待处理并保存ID/版本，不造新版或重置测试。新增分配平台编号，修改保留原展示编号并产生设计新版；成功应用的新增/修改同时完成审核，结果未测、人员为空，记录确认人/时间，旧执行记录归原版。
5. 停用保存独立操作历史，不物理删除用例；实施时须明确与当前“废弃”测试记录和逻辑删除的区别，不把设计停用偷换成执行结果。
6. 批次UUID与条目成功映射分别幂等，失败重试不重放成功项；同目标冲突操作失败待人工处理，其余继续。“已应用/已复用”须实际写入成功，失败项不假报审核完成。

更新利用可取得的旧需求/历史设计、新需求和当前人工版本，无生成基准仍可维护但标明证据限制。人工澄清结论在页面确认并保存来源/版本，用户随后只补生成受影响场景。首次500+在同一记录内按功能/输入计划自动分批，显示进度与多次本人AI调用提示，成功结果保留、失败批次人工重试，不静默追加计划外调用。

## 5. 用例分析

### 5.1 新建与输入

会话名称 → 审查方式 → 用例范围 → 需求/原型（按方式要求）→ 分析目标。

- 对照需求审查：至少一份实际可用需求/原型依据，必须声明用例范围。允许该范围当前为0条，用于识别明确缺失场景。
- 仅检查用例质量：至少一条用例；可检查内部矛盾、步骤不清、预期不可判断等，不能据此认定符合需求或项目覆盖完整。
- 用例范围支持全部、分类/筛选结果、勾选记录；发起时冻结内部ID和设计版本。只给编号而没有设计内容不能开始。

### 5.2 页面与结果

概览显示用例问题、缺失场景、需求待澄清、待处理数，不以覆盖率大屏为中心。右侧按三类发现筛选，并支持类型、等级、处理状态、关联用例筛选。

详情同时呈现需求预期、当前用例、存在问题、具体字段位置及修改建议。例如需求要求库存不重复扣减，而用例只检查提示，列出缺少的数据断言及双方固定依据。

缺失场景必须说明“在本次哪些用例范围中未找到”。只选部分用例不能断言整个项目没有该场景；未读取的需求部分不能算已经覆盖。正常用例在检查范围中留记录，不为其创建虚假问题。

完整新增/修改草案可直接进入与用例生成共用的人工应用流程，无需为同一草案重新调用AI。需求问题仅转成待澄清线索，不自动写回需求资料或新建已确认业务规则。

## 6. 代码分析

### 6.1 新建与输入

会话名称 → 检查目标 → 代码来源及范围 → 固定版本 → 需求/原型及可选用例 → 分析目标 → 本次发送范围确认。

检查目标可组合：代码Bug、需求符合性、前后端一致性。仅Bug检查允许没有需求；符合性需要实际需求依据；前后端一致性需要两端实际内容或可信协议依据，否则明确缺失环节。

- GitHub：选择本人有权限且项目已关联的仓库，固定提交；可选多个前端/后端仓库，分别记录版本，不凭分支名称推定两端属于同一部署。
- 本地代码：读取当前浏览器已授权范围并固定内容哈希。用户已授权本地读取不等于已授权上传后端/发送AI；正式实现前须确认发送与保留规则。
- 全部代码指授权业务范围，仍排除凭据、依赖和构建产物。指定范围外依赖只列缺口，不自行读取。
- 目录树、文件名、接口名均不等于已读取实现。输入必须包括实际内容、读取状态、仓库/快照、路径、行号或片段位置。

### 6.2 结果与详情

概览显示代码Bug、需求偏差、前后端不一致、证据不足/待处理数。卡片显示触发条件、预期与实际、影响、来源提交及静态/运行证据状态。

详情按以下顺序：

1. 功能与问题、等级理由、证据充分程度。
2. 触发条件 → 需求/协议预期 → 当前实现行为。
3. 页面操作 → 请求组装 → 后端入口 → 业务校验 → 数据查询/写入 → 返回映射 → 前端取值/展示。
4. 每个环节关联固定文件位置；未知环节显式标记，多个调用方和分支分别核对。
5. 前后端字段对照：接口/方法、JSON字段路径、类型、可空性、默认值、枚举、单位、时间/分页语义、前端读取位置。
6. 修复建议、建议运行验证、人工处理历史。

源码不铺满主页面；用户主动打开证据详情时展示支持结论的片段及文件链接。代码静态可确认的偏差与运行复现分开，未调用接口/数据库不能声称实际环境已失败。

例：后端返回verificationStatus，前端读取verifyStatus，需要继续核对序列化别名、DTO映射、默认值及最终展示，不能看到名字不同就直接报错。

不提供自动改文件、任意脚本或Git写入口；修复完成后用户选择新版本进行复核，关联旧问题并人工记录结论。

## 7. 变更分析

### 7.1 两种发起方式

同一菜单内选择“需求变更”或“代码变更”，保持原菜单不增加并列模块。

| 方式 | 必需输入 | 可选补充 | 缺资料时输出边界 |
| --- | --- | --- | --- |
| 需求变更 | 同范围新旧需求/原型固定内容，说明完整替换或增量补充 | 当前代码、用例、已确认业务澄清 | 可确认业务变化；未提供代码/用例不能判断其无影响 |
| 代码变更 | 明确基准与目标提交/内容快照，新旧实际内容及差异 | 当前需求、用例、已有发现 | 可确认所读实现差异；无旧内容不能断言问题是本次引入 |

GitHub分支、Tag、PR都先解析并固定具体提交。PR比较明确使用哪个基准及目标，不把基准分支当前头与共同祖先混为一谈。多个仓库分别展示比较对，不能相互比较提交。比较期间源分支更新不替换已保存基准。

本地两次读取的“加入范围/移出范围”与真实文件新增/删除分开；无旧快照时只能执行现状审查，不能生成伪造的差异。

### 7.2 页面与结果

累计区保留来源分析；概览统计变化项、受影响功能、待确认影响和建议回归项。分析记录展示新旧基准，详情提供新旧对照。

左侧功能范围，右侧按“业务变化、影响/风险、回归建议”切换。变化项说明业务含义；影响说明直接/间接、确定/可能/未知及传播链；风险归因区分本次引入、原有问题、无法归因。

回归建议包含优先级、功能/场景、现有用例ID及版本、建议保留/修改/停用/新增、推荐原因、前置数据和需要核对的结果。建议回归不创建测试通过记录，不自动执行测试。

需求变化可跳到“用例生成—按变化维护”，代码问题可跳到代码分析，但只预填本次范围和固定引用，用户核对并发起后才调用AI。已有完整用例草案走共用人工应用通道，不强制二次生成。

例：新增手动核销入口，检查新旧入口是否同样调用门店归属校验；回归既覆盖新入口的越权拒绝，也覆盖共用服务变动影响的原扫码入口。

## 8. 证据、版本与跨模块关联

建议在各模块自己的契约中使用明确类型的证据：资料版本/片段、用例内部ID/设计版本/字段、代码仓库或本地快照/路径/行号、变更前后版本/差异位置。语义支持性需要人工核对，不能只因ID和摘录匹配就视为判断正确。

- 所有对象使用项目＋模块＋分析ID＋本报告内key定位。F1/R1及用例展示编号都不是跨报告唯一键。
- 跨模块“带入分析”保存有来源的固定引用，原始资料仍是判断依据；不自动建设AI总结的共用知识库。
- 人工结论保留操作者、时间、依据版本；存在冲突时展示双方，不按最后一句聊天覆盖事实。
- 新版本复核可明确关联旧问题，保存复核结果与证据；旧问题不会因新分析没提到它而自动关闭。
- 报告保存、用例应用、人工新增分别校验幂等。批量应用与处理版本变化时拒绝过期操作。
- 每种模块可导入自己版本的input/report配对文件，校验分析类型、request_id、固定资料关联、完整性及所有引用；不向现有需求v3塞其他模块字段。

## 9. 权限、后台执行与本地代码边界

复用需求分析已确认行为：项目成员按项目权限共享结果和历史；每次发起/重试使用操作者本人AI配置；后台持久化后执行，离开页面不取消；仅发起人取消活动任务，失败手动重试；执行前后重查权限，外部等待不持有数据库事务。

同一对话同时只允许一个活动轮次；历史版本及请求UUID防并发串话/重复提交。上游真实上下文不足时明示失败，不静默裁剪、伪造完整检查或自动追加付费轮次。较大范围可由用户拆为多个明确分析，累计呈现。

本地代码若要采用“Web→后端→个人AI、离开继续、项目共享”，必须先将获授权的内容快照送到后端；只保存在浏览器时无法保证后台继续或团队复核。建议正式接入时采用“用户确认所选范围后，后端私有保存固定证据，按项目权限访问”，具体保存期限、删除规则、敏感内容排除和对AI发送范围需单独确认。此前本地只读授权不被本方案扩大。

Git仅固定读取白名单；不push、不创建/合并PR、不写远端文件。读取前展示仓库及范围，发现范围外依赖提示补选。用户资料和Skill均不能扩大系统权限。

## 10. 实现分工建议

继续使用core/db/security/integrations/api/modules分层。先落一个模块的真实闭环，再提取已产生复用，不预建通用Agent框架或空模块表。

| 可复用能力 | 复用方式 | 必须新增的模块差异 |
| --- | --- | --- |
| 页面主题、Form/Select/FilePicker/CaseDialog | 沿用现有组件和requirement-ui基础样式 | 各模块清单与详情内容 |
| 个人AI配置、Responses客户端、安全错误 | 直接复用既有接口与集成层 | 各模块输入/结果校验及提示词 |
| 后台持久化、取消、重试模式 | 扩展现有独立Worker明确领取已批准任务，不恢复旧analysis_worker | 按模块显式执行函数，防一个长任务永久挤占其他模块 |
| 用例管理 | 复用版本、权限、字段与事务写入规则 | 候选草案、审阅与应用记录；必要时提取真实共用服务 |
| 资料与代码来源 | 复用已有授权、版本和来源元数据 | 代码实际内容读取/私有快照及其授权边界 |
| 分析输入/报告/处理审计 | 共用约束和UI交互，保留模块契约 | 不让需求风险表承载所有异构结果 |

Skill建议分别放 `skill/case-generation/`、`skill/case-review/`、`skill/code-review/`、`skill/change-impact/`，含SKILL.md、契约及完整合成样例。目录仅是建议，本轮不创建空Skill。

接口与表结构在模块方案获准开发时列出具体清单再实施。本轮不发布不存在的API。新增表字段须中文数据库注释及Alembic迁移，后端架构/注释检查、前端请求/UI检查随改动执行。

## 11. 建议实施顺序与验收

1. 四模块总HTML原型：共用需求分析布局，先确认新建/累计/详情/历史对话以及全部状态；替换旧覆盖率主视图，不恢复验收点库。
2. 用例生成INITIAL＋人工应用：打通固定资料、候选、14列校验、判重、人工修改、版本冲突及幂等，形成共用用例建议应用能力。
3. 用例分析：接入用例快照、三类问题及修改草案；只读分析和业务应用分别验证。
4. 代码分析：先确认代码快照外发/保存边界，再完成固定内容、调用链与前后端对照；本地来源不得提前外发。
5. 用例生成UPDATE与变更分析：完善新旧基准、三方差异、人工改动保留、归因和回归范围，不用简单覆盖冒充增量维护。

关键验收场景：仅原型可生成但不造业务规则；用例编号重复仍准确定位；0条用例可对照需求识别缺口；部分用例不冒称全库遗漏；设计被人工修改后旧建议无法覆盖；应用重试不重复新增；只有前端时不伪造后端链路；改名/范围变化不冒充删除；无基准不认定本次引入；取消/断流不生成完整报告；普通聊天不改业务；切项目/功能历史不串；导出保留来源且不受分页限制。

## 12. 开发前需收敛的具体决策

| 决策 | 本方案建议 |
| --- | --- |
| 用例停用如何存储和展示 | 独立设计状态，保留旧执行历史；不要覆盖为“废弃”测试结果或删除 |
| 本地代码是否允许到后端及本人AI、保留多久 | 确认范围后私有保存固定证据；期限与删除语义由用户明确 |
| 跨模块引用如何进入 | 用户主动选择并确认带入，不后台自动串联/执行 |
| 先做哪一个正式模块 | 用例生成首次生成＋人工应用，再用例分析；若当前最急是核查已有用例，可先做用例分析只读清单 |

这些问题不阻止本方案和总原型的审阅；未确认前不默认实施新增写入能力、代码外发或数据保留政策。
