## 1. 页面定位

项目概览回答三个问题：项目已有些什么、哪些内容需要人工处理、最近的分析进行到哪里。

沿用 `/` 和「项目概览」菜单，只汇总当前选中项目，所有成员看到项目共享信息。概览提供有限摘要和返回所属模块的入口；记录详情、证据、对话、取消、重试、审核、入库和导出继续在原模块完成。独立「任务与报告」入口保持移除。

第一期建议展示：项目摘要、四张数量卡片、五类分析入口、需要关注、近期分析。不增加综合质量分、覆盖率、发布结论、人员排名、趋势图、通知或跨模块总报告。

已只读核对 `frontend/src/App.tsx`、后端模型及五类分析服务；这些是本地源码事实，不代表线上数据或当前服务运行状态。

| 当前内容 | 现状 | 本方案建议 |
| --- | --- | --- |

| 待确认验收点 | 占位，旧产品口径 | 改为资料与用例真实数量，不恢复旧验收点模块 |
| 用例完整覆盖 | 占位，缺少统一可信分母 | 移除覆盖率及覆盖进度条 |
| 本次需求的验证路径 | 静态步骤，项目没有对应的统一“本次需求”实体 | 改为五类分析快捷入口，不显示虚构完成步骤 |

## 4. 四张数量卡片

默认均为当前项目全量口径，不随「近期分析」的筛选变化。

| 卡片 | 精确计数口径 | 点击行为 |
| --- | --- | --- |
| 需求资料 | `source_document` 中本项目、`purpose=REQUIREMENT`、`deleted_at IS NULL` 的来源数量 | `/documents` |
| 原型资料 | 同表本项目、`purpose=PROTOTYPE`、未逻辑删除的来源数量；一个GitHub或链接来源算1个，不按页面数、文件树节点或版本数累加 | `/prototypes` |
| 活动用例 | `managed_case` 中本项目、未逻辑删除且 `lifecycle=ACTIVE` 的用例身份数量；不累计设计版本、测试记录或AI候选 | `/cases`，活动筛选 |
| 执行中 | 五类主分析记录中状态为 `QUEUED` 或 `RUNNING` 的记录数量；同一生成记录即使有多个历史批次也只算1条 | 本页执行中筛选 |

「执行中」卡片分列排队和分析中的数量。`PREPARED` 不计入；独立聊天、用例应用申请不混入主分析数量。应用失败在所属记录中另提示，不能把“分析完成”当作“应用完成”。

资料存在只证明平台登记了来源，不证明已解析、已分析或已核对最新远端内容。用例存在不等于已审核、已执行或测试通过。

## 5. 需要关注：按模块给出入口

名称采用「需要关注」，不称「我的待办」：目前问题并没有统一负责人、认领、截止时间和已读状态。本期不新增这些字段或流程。

保留五个固定模块行，每行显示少量分项数量及「去查看」。不将各模块不同性质的事项加成一个“项目缺陷总数”。

| 模块 | 拟展示的分项与计数条件 |
| --- | --- |
| 需求分析 | 待确认：风险当前状态 `PENDING`；待补充：`NEEDS_INFO`。包含原报告风险与已保存人工风险，排除 `RESOLVED`、`NOT_APPLICABLE` |
| 用例生成 | 分别显示「有待审建议的记录 X 条」「有待澄清事项的记录 Y 条」。前者至少有一条尚未成功应用且未忽略的候选；后者有按原模块规则仍未形成有效人工结论的业务问题。各分项按记录去重，两者可能重叠、不相加。有冲突或准备缺口的候选仍待人工核对，不写成可直接入库；成功应用的建议不重复统计 |
| 用例分析 | 待确认、已确认待处理：沿用现有中文处理状态；包含报告问题、说明事项与人工新增事项，排除已解决、不适用。草案已应用不自动将问题排除 |
| 代码分析 | 待处理、已确认、需补充证据分别统计；对应 `PENDING`、`CONFIRMED`、`NEEDS_EVIDENCE`，排除已处理和误报 |
| 变更分析 | 发现按待处理、已确认、需补充证据统计；回归建议另列待审阅 `PENDING` 和暂缓 `DEFERRED`。纯变化说明不算待处理发现；采纳不表示回归已执行 |

具体条目集合、默认状态和成功应用映射复用所属模块的现行口径，尤其用例生成要覆盖旧契约批次、人工候选和成功防重放；不能在概览另用AI文本或单一状态猜测。资料级、格式校验或证据警示不另算一条业务缺陷，原模块仍完整展示警示。

计数范围为项目现存报告/记录中的人工未关闭事项，不自动只取最新一次分析。相同业务问题在不同报告中出现时，按「模块＋记录ID＋条目ID」保留各自身份，不凭相似标题合并或自动关闭旧问题。区域说明标注「按历史记录累计，重复发现需人工核对」；未来如果需要按发布版本衡量当前质量，应另行确认版本/需求范围。

用例生成显示单位为「记录」，其他行显示各自「事项/风险/发现」，不混用单位。无关注事项的行显示0和普通入口，不显示“质量合格”。

## 6. 近期分析：有限摘要

默认显示当前项目最近创建的8条主分析记录或导入结果，按创建时间倒序；同时间按模块固定顺序和内部ID稳定排序。人工处理、聊天和轮询不改变创建时间，也不让旧记录反复占据首行。

记录显示：模块、名称、发起人或导入人（已有可核实字段才显示）、创建时间、执行状态、结果完整性、查看入口。名称为空使用模块名称和真实编号，不编造业务标题。

- 「全部」包含待开始、排队、分析中、完成、失败、取消及导入结果。
- 「执行中」先按排队/分析中条件过滤，再取8条；不能先取最近8条再过滤而遗漏较早的在执行记录。
- 「已完成」按执行状态为已完成过滤，再取8条；结果部分完成的已结束分析也包含在内，结果完整性另行显示。此页签由用户于2026-10-14进一步明确要求，已同步原型。
- 「失败」显示真实失败分析记录。旧失败在后来重试成功后仍是历史失败；只有现有明确重试关联才展示后续记录提示，不自行推断失败已经解决，也不自动付费重试。
- 四个筛选各自最多8条，不做全历史分页、全局搜索或第二套报告清单。说明「更多历史请进入对应分析模块」。
- 需求分析任务和其 `report_id` 指向的报告只展示一行；没有关联任务的导入报告单独展示，显示「导入结果」，不伪造排队和执行过程。其他模块的导入记录沿用实际来源信息。
- 执行状态和结果完整性分别展示。例如「已完成 · 部分完成」，不能压成绿色“全部完成”；取不到可信结果完整性时显示「完整性待查看」，不能用列表摘要里的空值推断完整。
- 部分完成、依据不足展示短提示；失败展示既有脱敏错误文案。原始模型响应、资料正文、堆栈、密钥、模型配置详情不进入概览。
- 用例生成/用例分析如有真实应用失败且对应建议尚无成功映射，额外显示「有入库失败项」，点击仍进入对应记录核对；后续已成功的条目不继续报待处理失败，原失败审计仍保留。不把该标记混成AI分析失败。

## 7. 跳转与权限

沿用当前项目权限：有效平台管理员、项目负责人和项目成员可读；非成员不返回项目统计、记录名称或数量。项目共享记录不按发起人过滤，个人AI/GitHub配置始终不共享。

五类列表当前主要在组件内部保存选中记录，不能假定已有通用深链接。后续开发需补齐最小跳转能力：各模块仅接受自己允许的记录类型/ID和既有筛选值，进入后从服务端重新鉴权读取。具体查询参数在开发时统一确定，不把本方案中的展示字段直接当API。

单条「查看」必须定位到该记录；关注摘要必须准确应用该模块的未处理状态组合。目标不存在或无权访问时显示应用内提示并提供返回模块入口，不能悄悄显示另一条记录。刷新后可以恢复目标；浏览器前进后退保持合理的项目和筛选上下文。

切换项目立即清除旧项目统计及旧请求结果；迟到响应须复核当前账号和项目。退出登录或撤权后清除缓存。概览不执行取消、重试、审核、批量入库、资料更新或Git操作。

## 8. 数据读取与工程方案（候选）

建议新增只读 `GET /api/projects/{project_id}/overview`，接受固定的近期分析筛选（全部/执行中/已完成/失败）。返回汇总时间、四卡计数、五类关注摘要、最多8条近期记录以及各区块的可用状态。该接口当前不存在。

前端独立 `ProjectOverview` 和对应API文件，App仅负责装配；复用公共HTTP、主题按钮/页签和错误处理，不在App继续堆叠统计与请求逻辑。

后端如实施，使用小型 `modules/overview` 的router/schemas/service。router只转协议；service先鉴权，通过各所属模块新增或已有的公开只读摘要函数组合结果。模块之间不通过HTTP相互调用，不让原分析模块反向依赖overview，不引入通用任务注册框架。

现有数据来源：

| 内容 | 已有事实来源 | 后续需要补齐 |
| --- | --- | --- |
| 项目/资料/用例 | `project`、`source_document`、`managed_case`；已有项目权限和列表服务 | 服务端准确计数与概览字段投影 |
| 五类执行状态 | `requirement_risk_analysis`、`case_generation_run`、`case_analysis_run`、`code_analysis_task`、`change_analysis_task` | 固定身份和状态映射，主记录去重 |
| 需求导入与关注项 | `requirement_risk_report`、`requirement_manual_risk`、独立handling | 任务与报告去重、人工风险一并计数 |
| 其他模块关注项 | 各自报告/handling；生成还包括批次和实际成功应用映射 | 共用现有业务口径的最小摘要能力 |
| 入库失败提示 | `case_generation_application`、`case_analysis_application` 的真实条目结果 | 有界摘要，不返回整份申请内容 |
| 精确跳转 | 已有五类页面和记录详情API | 页面读取目标ID/筛选并处理权限、缺失与刷新 |

不在浏览器把各模块所有分页和完整报告下载后求和，也不把现有列表第一页当项目总数；已有JSONB结构需要在服务端定向提取，不在概览重复读取固定资料/源码/附件正文。不借用需求累计清单的全量明细响应冒充轻量摘要。

优先使用现有表，不新增概览表、统一任务表、统计快照、迁移、缓存中间件或Worker。大项目历史JSON处理成本和实际响应时间尚未测量；开发时必须验证，不能承诺固定性能。若准确计数确需持久统计字段或迁移，先说明新增范围，不能静默降级成截断估算或伪造总数。

## 9. 更新、空数据与失败

- 首次进入及切项目读取；提供手动刷新。页面可见且执行中数量大于0时建议每10秒刷新；无在执行任务不持续轮询，重新获得页面焦点时刷新。概览看不到其他页面新建的任务时，可在回到页面或手动刷新后发现。
- 统计显示本次成功读取时间；不同区块可能来自同一汇总窗口内的不同查询，不宣称数据库全局原子快照。部分失败需单独标记，不能沿用一次新时间把旧数据当最新。
- 本项目旧数据刷新失败可保留并标注「更新失败，显示上次数据」；新项目不得先展示上个项目的数据。
- 项目无资料、用例或分析时显示真实0和各模块入口；没有选择项目时只提示先选择项目，不发送项目统计请求。
- 单模块摘要失败不变成0，也不使其他成功区块失效；鉴权失败、账号失效和撤权属于整页失败，遵循公共登录/权限处理，不继续泄露已缓存内容。
- 「近期分析无记录」「筛选无匹配」「读取失败」分别展示；统计0不推出没有风险或项目可以发布。

## 10. 验收与后续顺序

先审阅本方案，再按用户指令同步已有总HTML原型；原型确认后才按授权开发。此次设计不构成原型或业务开发授权。

后续至少验收：

1. 项目隔离、切项目迟到响应、退出/撤权；所有数字有明确来源，空、失败和未知均不伪造0。
2. 资料按来源计数、排除逻辑删除；活动用例排除停用，版本不重复；主分析不重复统计批次、聊天和应用。
