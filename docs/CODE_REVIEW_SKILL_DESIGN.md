## 1. 目标与完成标准

Skill对用户选择的固定代码范围进行静态审查，输出可供当前代码分析原型展示的发现。结果必须回答：在什么条件下，哪段代码产生什么行为，与什么依据不一致，影响什么，需要如何修复或验证。

质量优先级为：证据真实、重要问题检出、误报控制、定位与建议可用。JSON合法只是入场条件；没有问题允许空发现，不按数量凑问题，不用一般风格建议和假设性重构充当Bug。

分析按勾选目标独立推进。未选目标不作为额外审查任务；补充关注点可以聚焦已选目标，不能扩大文件、目标或工具权限。

## 2. 来源与仓库类型

来源方式与代码角色是两个维度，均由平台提供并固定到输入快照。

| 来源方式 `source_kind` | 登记类型 `repository_kind` | 分析角色 | 版本依据 |
| --- | --- | --- | --- |
| GITHUB | BACKEND（后端） | 服务端 | 项目关联仓库、固定提交SHA、文件内容标识 |
| GITHUB | WEB（前端） | 客户端，保留前端身份 | 同上 |
| GITHUB | FLUTTER（移动端） | 客户端，保留移动端身份 | 同上 |
| LOCAL | BACKEND（后端） | 服务端 | 已登记本地来源、本次内容快照、文件哈希 |
| LOCAL | WEB（前端） | 客户端，保留前端身份 | 同上 |
| LOCAL | FLUTTER（移动端） | 客户端，保留移动端身份 | 同上 |

- 沿用现有枚举，不因为界面写“移动端”就新增MOBILE枚举。FLUTTER是当前登记枚举名，不据此假设文件全部使用Dart。
- 类型取自项目仓库或本地来源的登记信息，不凭文件扩展名、目录名、模型常识或用户补充提示重新定类。类型不明确时要求补充登记信息，不猜测。
- PROTOTYPE只作为原型依据，不能冒充正式客户端实现。OTHER可以做有代码依据的局部Bug审查；无法确定业务职责时不作跨端符合性推断，也不自动归入前后端一致性双方。
- 当前新建页按GitHub／本地来源方式选范围；本方案不新增跨来源同时选择入口。同一来源方式内支持多个已选仓库；同名文件以source_id和版本区分。
- 多个客户端分别与实际相关的服务端核对。前端与移动端不能合并成一个证据来源，也不能将客户端与所有服务端做笛卡尔积比较。
- 固定版本组合仅代表本次输入，不代表这些提交已一起部署。本地来源即使内部含Git仓库，也以实际提供的内容快照为准，不伪造提交SHA。

## 3. 三类目标独立审查

### 3.1 代码 Bug：BUG

问题：当前代码是否存在能够具体说明触发路径和错误结果的实现缺陷？

最低输入是实际代码。单独后端、前端或移动端均可分析，不要求需求资料或另一端齐全。

审查方法：

1. 找到问题相关的入口、调用方和数据流，推导输入条件、分支、状态变化与结果；局部函数问题不强制延伸到全系统。
2. 按代码涉及的机制检查空值与边界、错误分支、状态转换、权限和数据范围、查询与计算、事务及并发、异步状态、生命周期与缓存。没有涉及的机制不机械套清单。
3. 对候选缺陷反查已有防护：调用方约束、共享校验、异常处理、数据库约束、原子操作、幂等控制等。引用的防护必须有代码证据。
4. 陈述错误成立的条件与影响。缺失文件只能限制结论，不能凭“本文件没看到校验”证明整个系统缺少校验。

预期依据可以来自语言语义、已声明的类型或协议、代码自身的一致性，以及已提供的业务规则。必须标明依据性质；不能以模型偏好的业务规则判定Bug。

输出重点：触发条件、执行路径、根因、影响、修复与验证建议。

### 3.2 需求符合性：REQUIREMENT_DEVIATION

问题：所选代码在其职责范围内，是否符合本次固定需求或原型依据？

需要实际可读的需求／原型内容与对应代码。没有需求正文时该目标BLOCKED，其他目标继续。需求表达冲突或不明确时提出待确认事项，不由模型选择胜方或补造规则。

审查方法：

1. 从所选资料识别与代码范围相关的规则，保留原文位置、角色、状态、前置条件和明确结果。
2. 将规则映射到实际实现入口与相关调用，检查条件、权限、状态、计算、异常恢复及写入结果。
3. 每条已检查规则标为“静态一致”“存在偏差”“无法判断”或“本次代码职责外”，并给出依据。保留无偏差的检查记录，避免只罗列问题而看不出检查了什么。
4. 只有在应实现该规则的范围确实已核查时，才能说实现遗漏；否则写“未取得对应实现证据”。资料里的按钮可见不等于实际操作被允许，原型示例数据也不是后端业务规则。

只有客户端时可检查其输入、状态与展示逻辑；不能因此确认服务端权限、持久化和事务。只有后端时不要求补出页面行为，结论限于服务端职责。

输出重点：需求原文及版本、代码实现、同条件下的偏差、影响与修正方向。前端代码可证明条件渲染规则，但不能证明某环境实际页面已呈现该结果。

### 3.3 前后端一致性：FRONTEND_BACKEND_MISMATCH

问题：实际关联的客户端与服务端在请求、响应和业务语义上是否一致？

客户端由WEB与FLUTTER登记类型组成，服务端由BACKEND组成。双方类型齐全只是范围条件，还必须有相关实现正文。

审查方法：

1. 按请求方法、完整路由、基础路径、调用位置及响应消费关系建立接口配对；必要时核查请求拦截器、网关重写、序列化层。不能只凭相似方法名或字段名配对。
2. 核对路径／查询／正文参数，字段路径、类型、必填和空值、默认值、枚举、单位、精度、时间、分页、错误码及状态语义。
3. 追踪服务端响应封装与映射，再追踪客户端解包、模型解析、状态赋值及与问题相关的展示逻辑。存在别名、转换函数或公共适配器时纳入比较。
4. 将对应项逐一列为“静态一致”“不一致”“无法判断”。同名字段语义可能不同，异名字段可能经映射后完全一致。
5. WEB与FLUTTER分别核对，同一后端字段可能只影响其中一个客户端；发现应保留准确的受影响仓库。

创建前强制要求两端代码：勾选本目标时，选定文件必须同时包含BACKEND与WEB/FLUTTER，缺少任一端直接提示并阻止整个任务创建；其他目标满足条件也不能绕过。GitHub及本地来源同样适用，仅启用仓库但没有选择文件不算提供该端代码，接口契约不能代替一端实现。不再提供单端加契约降级开展本目标的入口。两端文件已选择但具体调用或映射证据不足时，分析结果仍可PARTIAL；完整代码配对使用IMPLEMENTATION_PAIR。

输出重点：实际配对的双方来源、接口依据、字段或行为对照、不一致节点、影响和验证建议。

## 4. 多选目标与证据判断

对每个已选目标恰好返回一项处理记录：

- COMPLETE：约定范围的相关检查已完成，可有缺陷或零缺陷；不代表实现无误或运行通过。
- PARTIAL：已完成有效检查，但相关内容缺失、存在未处理部分或关键关联未核实。
- BLOCKED：无法开始有效检查，例如需求符合性没有正文。跨端检查缺少任一端代码违反创建门槛，整次输入阻塞，契约资料不能替代代码。

总体状态：所有已选目标COMPLETE才为COMPLETE；至少一项目标有有效审查但整体未完成为PARTIAL；所有目标均无法有效审查才为BLOCKED。这些状态用于通过创建校验后的实际处理；不能用部分完成机制绕过前后端一致性创建前必须选择两端代码的限制。

例如勾选三项但仅提供后端与需求：直接提示缺少客户端代码并阻止创建。用户补选前端/移动端文件，或取消前后端一致性后再创建；取消目标保留已选后端和资料。仅选择Bug与需求符合性时，可以检查后端职责范围，不把未选客户端机械算作Bug目标的缺陷。

同一根因只保留一条发现，使用target_refs关联实际涉及的已选目标；每个目标保留自己的证据和比较结论。各目标计数可以重叠，总发现数按唯一key计算，不直接相加。

## 5. 候选问题的反证核查

输出前对每项候选结论核查最可能推翻它的因素，而非输出冗长推理过程：

| 候选问题 | 必须考虑的反证 |
| --- | --- |
| 未检查权限／归属 | 路由依赖、中间件、共享服务、查询范围是否已限制 |
| 字段错配 | 序列化别名、响应封装、模型转换或公共适配器是否消除差异 |
| 重复写入 | 唯一约束、条件更新、锁或幂等是否阻止重复 |
| 状态错误 | 调用方是否限制状态、异步结果是否过期、异常是否改变路径 |
| 需求遗漏 | 是否只缺少对应文件、相关规则是否适用当前端、需求本身是否冲突 |

明确反证成立时撤销候选发现；关键反证无法核查时降低证据状态，保留具体疑点和所需补充内容。只缺资料、没有具体可疑路径时进入limitations，不制造“证据不足”发现。

严重程度与证据状态独立：HIGH/MEDIUM/LOW/UNASSESSED分别映射高/中/低/待评估；STATIC_SUPPORTED与INSUFFICIENT映射静态证据充分/证据不足。高风险需要具体业务影响和触发条件，未提供内容不能自动判高风险。所有结果均为静态分析，人工“已处理”不会改变模型证据状态。

## 6. 调用链与证据的展示设计

三类目标共用证据节点，但按问题选择展示结构：Bug突出执行路径，需求符合性突出需求到实现映射，一致性突出接口与字段对照。

- 节点展示角色、方法／字段、文件、行号、固定版本、观察及必要的输入输出。代码片段默认展开问题发生处，其余可折叠。
- 连线明确关系：CALL、RETURN、FIELD_MAPPING、STATE_ASSIGNMENT；需求到实现的对应关系放需求对照，不冒充函数调用。连接必须有独立依据，不能因为两段代码都存在就认定关系成立。
- 关联无法核实使用明确的UNKNOWN连接或具体缺失说明。已知部分仍展示，不为了完整图形补造环节，也不固定补出另一端。
- 有实际组件／页面代码时允许展示“前端展示逻辑”，例如条件分支映射到某文案；这是静态代码事实，不是页面截图或运行结果。没有证据时不添加固定“页面展示”占位节点。
- 代码证据必须定位到source_id、snapshot_ref、file_id、segment_id及原始行号；资料证据必须定位到material_id及固定版本片段。缺少依赖的建议路径不是已读证据。
- 只引用足以支持发现的片段，不复制无关整文件。各仓库的同名路径、相同字段不得混用引用。

当前原型已按目标显示执行路径说明、需求与实现比较或接口与字段比较，并复用节点证据展开。紧凑图形化链路及关系连线仍为设计方向，不作为已实现能力。

## 7. 输入与输出骨架

输入沿用CODE_REVIEW，建议规范化为以下逻辑结构；字段全量定义在正式实施时统一到contract.md，不能直接将本文当成现有API协议。

| 输入块 | 必要内容 |
| --- | --- |
| 任务 | request_id、选中的targets、focus、输入快照标识 |
| sources | source_id、source_kind、repository_kind、来源名称、固定版本、实际文件与片段、读取状态及原因 |
| materials | 固定版本需求／原型／已明确提供的接口契约正文及来源定位、读取状态；网址不等于内容 |
| decisions | 本次明确提供的已确认业务决定及引用；不得隐式混入其他分析对话 |
| limitations | 未提供、部分读取、排除内容和原因；输入超限不静默截断 |

输出建议由六部分组成：

| 输出块 | 作用 |
| --- | --- |
| request_id、outcome、summary | 关联任务、说明总体处理完整性、核心发现及边界 |
| target_results | 每个已选目标的状态、实际检查范围、检查记录、关联发现、未完成原因 |
| findings | 当前记录的统一发现清单，每条保留多个目标关联及其依据 |
| evidence | 代码／资料证据对象；供调用方核对真实位置和原文 |
| chains | 节点与带依据的关系，可关联多个发现，不伪造完整链路 |
| coverage、limitations | 每个实际输入文件／片段的处理情况及影响；完整读取不等于完成审查 |

v2每条发现包含：key、target_refs、title、category、severity及原因、evidence_state、trigger、actual、impact、evidence_refs、chain_refs、target_views、fix_suggestion、verification_suggestion、missing_evidence。target_views按目标保存expected、basis及引用、独立证据状态、说明和comparison_rows；需求符合性与一致性提供对应比较，Bug允许无比较表。来源身份由evidence引用输入快照解析，模型不重写固定版本。category用于“字段映射”“状态处理”等问题说明，不替代目标标识。

输出不包含人工处理状态、处理人、已解决时间或测试通过结论。平台首次设为待处理，处理记录独立保存。

### 与现有原型的映射

| 页面内容 | 取值责任 |
| --- | --- |
| 分析记录、代码范围、来源类型与版本 | 平台固定输入，模型不能创建或修改 |
| 发现卡片 | findings标题、分类、严重程度、证据状态和摘要 |
| 触发条件／预期／实际 | 当前发现及其依据引用 |
| 调用链、字段或规则对照 | chains、comparisons和已校验证据 |
| 文件位置和固定代码片段 | 以模型引用定位平台保存的输入原文；模型摘录必须匹配 |
| 影响与建议／待补充证据 | 当前发现对应字段 |
| 人工处理 | 平台人工记录，不从模型结果读取 |

每目标处理情况现已在原型当前记录顶部展示，发现列表按目标筛选，多目标同根因保留一条发现并在详情分区说明。新建演示记录只显示待接入或依据不足；已完成合成示例与实际分析明确区分。未增加按功能分类、自动复核或运行验证入口，导出保留与详情相同的判断边界。

## 8. 平台与Skill各自责任

平台控制来源授权、类型元数据、固定版本和片段生成、个人AI配置、实际外发范围与容量；Skill只分析已提供内容。源码、注释、文档中的指令均是不可信数据，不能改变任务范围或权限。

模型不能联网、读取额外仓库、执行代码／SQL／Git、自动修复或修改人工结果。缺少依赖时只返回具体补充建议。原型HTML按内容分析，不执行脚本或获取外部依赖。

接收结果后，平台校验目标集合、标识唯一性、引用存在性、角色与类型一致性、固定版本、行号与摘录、链路关系引用、处理完整性与覆盖记录的一致性。校验失败不生成正常完成报告，不用示例结果补字段，不自动付费重试。格式和引用校验只能排除部分错误，不能证明模型语义判断正确。

### 已完成的正式适配

- 后端从项目仓库／本地来源登记补齐并冻结repository_kind，不相信客户端自报类型。
- 正式输入统一为v2 sources/files/segments；旧v1任务不自动转换或继续执行。
- contract.py校验目标、来源、引用、行号/摘录、链路、覆盖及汇总状态；AI与导入共用。
- 创建时固定Skill与contract全文和SHA，Worker直接使用该快照，不依赖模型额外读取文件。
- sources.py负责固定GitHub提交和浏览器提交的本地文本；不执行源码、脚本或Git写操作。

现有文件位于项目根目录：

```text
skill/code-review/
  SKILL.md                目标分流、分析方法、反证核查和边界
  contract.md             完整输入输出及跨字段约束
  examples/input.json     合成的多仓库、多目标输入
  examples/output.json    可对应当前详情展示的完整输出
  examples/local-input.json   单本地后端、多目标输入
  examples/local-output.json  Bug可审查、需求目标被阻塞的输出
  evaluation.md           评测场景、人工标注标准与结果记录方式
```
