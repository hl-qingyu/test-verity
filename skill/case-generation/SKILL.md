# 用例生成

根据本次提供的完整资料设计用例，一次完成理解、设计、比较和自查，按 [contract.md](contract.md) 只返回 `cases / notes / complete`。把输出空间用于具体用例和必要说明，不输出推理过程、规则树、场景树、状态图或逐片段覆盖台账，不制定分批或额外调用计划。

调用方按 [resources.json](resources.json) 的顺序提供本文件、完整参考规则和当前契约；所有运行规则均须结合本次资料理解。相对链接用于定位规则职责，不代表模型可以自行读取磁盘、联网或调用工具。完整文件夹可独立复制；离线调用者也须提供清单中的实际正文，只有本文件和链接不足以应用完整规则。

## 本次设计顺序

1. **确认范围与资料身份。** 确认生成模式、所选功能、端、角色、资料侧别、旧新关系、关注点和选定用例。完整阅读正文、表格和对应/公共批注；目录、URL、哈希或标题不能替代内容。
2. **从当前依据理解业务。** 逐项识别对象、角色、条件、动作、限制和结果，不从已有用例倒推需要覆盖什么。疑似缺规则时先按证据规则复查已提供的全部关联内容；局部冲突不阻止其他明确分支。
3. **检查适用路径。** 核对正常、拒绝、边界、状态、时序和风险分支；有生命周期时检查状态连续性，有跨端协作时核对入口和观察位置。以结果差异和实际风险决定组合，不机械乘出全维度用例。
4. **设计具体用例。** 每条一条确定路径，保留同一路径的相关断言。选择最小必要初始条件和可区分输入，写清角色、对象、操作顺序、预期及必要恢复。计算结果须能从所列样本按明确公式复核。
5. **比较所选已有用例。** 当前依据决定场景，已有用例仅用于匹配；完全满足优先REUSE，明确差异才UPDATE，无对应才NEW，明确不再适用才RETIRE。保护已有人工字段，不按标题或展示编号猜目标。
6. **复查粒度与优先级。** 删除无关条件和真正重复的场景，保留独立边界、角色、拒绝原因、时点和路径；逐条根据失败后果定级，不套关键词、默认等级或固定比例。
7. **回到原始资料反查遗漏。** 对照本次完整所选范围检查每条明确限制、分支及结果是否得到承接，尤其是表格、否定句、例外、批注、进行中业务及历史数据。发现可补齐的设计继续完成，不用“尚未建模”提前停止。
8. **检查输出并分类剩余缺口。** 校对必要字段、真实目标、有效来源、连续原文和完成声明。只输出契约JSON，不附过程文件或自报已通过的审查记录。

上述顺序是同一次调用的设计要求，不是平台已执行的隔离阶段。已有用例与当前资料可能同时提供，不能声称实现了模型不可见历史的盲发现或独立覆盖证明。

## 候选质量与完成声明

新增用例必须填写非空的 `title / steps / expected / structure / case_type / priority / description`，其余设计字段按实际需要填写字符串。UPDATE仅提供必要变化，省略保留人工值，空字符串表示明确清空；REUSE/RETIRE不携带重复设计。不要因新增字段要求把应复用的内容改为新增或覆盖人工值。

业务条件、动作和结果明确时，即使账号、数据、权限、观察入口或故障控制方法待准备，也继续生成待审阅设计，将具体缺口放在 `data_requirements / remark`，必要时添加 `EXECUTION_SETUP`；不能编造可用工具、接口或SQL补齐步骤。

剩余说明仅有三种：`BUSINESS_QUESTION` 表示缺决定性业务预期或存在未解决的实质冲突；`EXECUTION_SETUP` 表示执行准备待补；`UNFINISHED` 表示资料不可用或本次设计未完成。说明具体范围、已知内容及所缺事项，不混淆产品决定、执行准备和模型遗漏；不要把每个启发式维度都变成问题。

有业务待确认或未完成范围时 `complete=false`；只有执行准备缺口且明确业务范围已设计完成时可为true。它只是模型对本次范围的声明，不等于平台已证明语义覆盖、用例已审核、已可执行或测试通过。

正式编号、建议key、补丁before、审核、测试结果、人员和应用审计由平台管理。人工确认后由系统直接逐条入库；成功项保留、单条业务失败继续、复用保留原设计与测试历史。本Skill不执行写入。
