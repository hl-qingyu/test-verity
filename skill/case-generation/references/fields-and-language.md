# 字段职责与直白表达

## 十二个字符串设计字段

| 字段 | 内容 |
| --- | --- |
| module | 本次资料中的所属功能模块；同类统一命名，不凭文件名发明模块 |
| structure | 子功能、页面或业务操作；必要时说明角色视角，不用来源编号代替 |
| case_type | 按本条重点选择，如功能需求、业务流程、逻辑校验、异常用例、边界用例、兼容性用例；不凑类型 |
| priority | 按priority规则选择P0–P4，并在remark给具体理由 |
| description | 简短说明验证目的或业务场景，不复制title或expected |
| title | 点明对象、关键条件和验证结果，不写“链路校验”“业务规则”等占位标题 |
| preconditions | 开始前必须成立的身份、状态和必要数据，不夹本次操作 |
| steps | 按顺序分行编号，明确谁对什么对象做什么，变化时写角色和端 |
| expected | 可检查的表现、值、状态、记录或数量变化；相关断言可分行 |
| data_requirements | 具体待准备的账号、对象、样本、造数、环境、外部配合与观察方法 |
| cleanup | 必要且有依据的恢复和清理；不需要时留空 |
| remark | 优先级理由、实际限制和必要准备提醒，不重复正文或内部分析过程 |

NEW必须有具体非空的structure、case_type、priority、description以及title、steps、expected；不要用“暂无”“待补”满足字段。其余字段按实际需要填写。UPDATE只发必要变化，REUSE/RETIRE不重复设计，不为字段齐全覆盖人工值。所有design值均为字符串，不输出数组或新字段；十二字段中的十列仍映射原14列。

## 执行人员读得懂

连读前提、步骤和预期，应能知道准备什么、做什么、检查什么。保留资料中的页面、按钮、字段和状态原名，术语必要时说明含义。不把内部引用编号、英文契约枚举、规则树和“语义闭环”等分析用语塞进正文。

步骤写动作，不写“提交成功”“触发异常流程”或“按条件执行目标操作”；预期写断言，不写“检查是否正确”“正常显示”“符合需求”。失败路径写清拒绝的操作及有依据应保持的数据，提示文案、秒数和精度只有资料明确时才填精确值。无入口时按准备规则处理，不能为了更具体而编造按钮和SQL。

前提不重述全部准备历史；步骤不复制前提或夹带结果；预期不复述步骤；备注不重复整条设计。不机械删词、限定字数或截断必要内容，简洁不能省略影响执行的条件、单位、数量、时点和对象。动作词和结果词仅为提示，不是允许词白名单；未命中示例词不能作为不可执行或不可判断的结论。

## 对象命名

优先用资料中的业务名称。同类多对象可用“订单1、订单2”“操作员1、操作员2”区分，但不能冒称真实ID。输入没有名称时使用对象类型、业务关系和已明确的初始状态，不用“免检账号”“必然成功订单”等名称偷带预期。

确有实际数据别名时首次解释，后续保持对应；不把对象标题当对象身份。用例编号、case_ref和来源引用只用于结构化身份，不能变成业务对象名称。代词必须唯一，“该数据”“相关状态”不能指多个对象。不编造测试文件、账号、日期或技术格式串作为现成准备资产。

## 说明文字

note写本条必要比较原因、限制或人工冲突；notes只写具体业务问题、准备缺口或未完成范围。不要每条重复“未执行、不保证、待人工审核”等通用免责声明。优先级为AI建议等实际来源需保留；生成内容本身不写审核、测试和入库状态。
