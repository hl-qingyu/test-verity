# 最小前置与执行准备

## 先判必要性

对每项条件回答：删掉它后，哪一步无法执行，或哪个结果会变化、无法判断？只有影响本条入口、分支、输入、归因或结果的内容才保留。不要自动附加账号正常、组织启用、业务日期固定、无并发、已同步等背景；也不能将无关条件搬到备注伪装精简。

已有角色与权限足以表达准入时，不展开全部上游开通历史。为区分相同拒绝现象需要排除具体混淆原因时保留，例如验证组织黑名单时排除会造成同样拒绝的个人拉黑；不枚举全部正常状态。通常少量短句即可，不能用固定条数、字数或长句压缩代替必要性判断。

## 内容分层

| 内容 | 位置 |
| --- | --- |
| 必要身份、权限、对象初始状态和简短样本 | preconditions |
| 本次输入、点击、提交、切换和观察动作 | steps |
| 长样本、造数方法、外部配合、环境与故障控制 | data_requirements |
| 直接可判断的状态、数值和结果 | expected |
| 需要的恢复或清理动作 | cleanup |
| 比较限制、准备提醒、优先级理由 | remark |

不重演准备历史：只验证重新申请后的编号时，前提写旧申请和新申请的必要状态；若目标就是重新提交，提交动作留在steps。可替代角色、入口、来源状态和输入类别分成确定路径；必须同时存在的纳入/排除样本可在同条使用，不写执行者任选的A/B路径。

## 数据依赖决定准备粒度

简单入口、展示或普通编辑只准备本条最小有效对象，不复制全套交易和统计样本。字段校验明确目标值，其他无关必填字段可保持合法值；组织、币种、时间等影响结果时才具体展开。计算样本按计算规则，筛选样本必须能区分本条关注的纳入和排除结果。

输入样本可根据明确约束设计，但注明为拟准备测试样本，不声称是真实已有记录或产品阈值。需要避免重名时写“未被占用的名称”，不提供虚构现成ID和文件路径。没有真实准备文件时，把必要数据直接写入本条；不能写“见公共数据”或引用不存在的附件来隐藏缺口。已有准备引用须能在本次提供内容中找到准确目标及使用范围，不能自行访问磁盘补读。

## 受控故障与外部配合

失败、延迟、回调、并发或跨端准备须说明对象、触发时点、已提供的控制方式和恢复方法。资料没有方法则写“执行前需准备在提交已发出后暂停对应处理的方法”等具体缺口，不编SQL、接口、工具名或账户权限。业务明确时继续生成，用data_requirements和EXECUTION_SETUP保留准备要求。

其他角色在测试开始前完成的动作放准备；本次被验证的外部变化按时点写入steps。cleanup只写需要且有依据的恢复，不编造删除历史交易、重置余额等操作。

## 自查边界

连读前提、数据、步骤和预期，检查每项准备是否真的服务本条。同模板可以复用共性判断，但不同数据和分支分别核对，不能将整套公共样本铺到每条。缺现成账号或观察方法不降低业务优先级，不转为产品问题；是否允许该角色操作或业务结果本身未知才属于业务决定。不要输出“已语义复核通过”一类签名，文字齐全与哈希一致不能证明准备合理。
