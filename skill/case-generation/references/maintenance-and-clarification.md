# 已有用例维护、澄清与历史保护

## 当前依据先行

首次生成允许没有已有用例。无论INITIAL还是UPDATE，先从当前有效依据理解应测路径，再比较调用方选定的固定用例；不要复制旧用例的条件、阈值和预期充当当前规则。已有用例可提供检索和差异线索，但每个确定结果仍须回到有效业务依据。

本次同时提供已有用例不构成物理隔离的盲发现，不声称模型未看过历史。只比较所选集合，不声称查重全项目。没有历史生成记录不阻止维护导入或人工用例，也不伪造旧基准、人工改动来源或三方保护结论。

## 四类动作

| 动作 | 条件与输出 |
| --- | --- |
| REUSE | 已有用例的条件、角色、关键输入、动作、时序和相关断言完整满足；target真实，不携带design |
| UPDATE | 同场景存在明确必要变化；target真实，仅发送改变字段，note写具体依据及人工冲突 |
| NEW | 没有完整对应场景，提供非空必要字段和有效来源，不复制同场景重新编号 |
| RETIRE | 当前明确不再适用且具备平台认可的旧新配对或确认结论；target真实，不携带design |

target只用输入case_ref，不能按展示编号或标题猜case_id。REUSE不重置设计、优先级、测试结果、人员和历史。UPDATE省略字段保留原人工值，空字符串是明确清空；不能为统一风格重写无关内容，也不能因NEW字段完整性要求覆盖已有structure、case_type、priority、description。data_requirements和cleanup虽不直接显示为14列仍须保护。

相似标题不代表同场景；角色、输入、边界、拒绝原因、时点和观察结果任一有独立差异，应按实际设计处理。仅缺部分断言时不能无说明REUSE。维护的理由写note或remark，不要求模型输出before、平台补丁或审核状态。

## 旧新关系与停用

按输入确认的完整替换或增量补充关系比较。增量继续继承未被替代的有效旧规则；新版未提、页面未选、读取失败、改名或移出模块都不证明删除。RETIRE须有明确当前取消或不适用依据，且符合契约来源绑定，不用来源缺失代替停用理由。停用不等于删除，也不等于测试结果“废弃”。

有真实基准时区分旧生成值、当前人工值和新依据，人工同字段变更冲突保留待核对说明；没有基准只说明比较边界，不称已保护全部人工修改。不要自动回退人工值或清空未提供字段。

## 人工澄清与补生成

仅平台核实的有效decision_ref可以代表已确认结论，聊天建议、待确认产品意见和示例不自动转为业务依据。结论须在输入中具有适用范围和当前有效性；冲突或替代关系未知时保留业务问题，不因日期最新自行覆盖。

澄清补生成仅处理本次确认受影响范围及必要关联，沿用当前契约输出建议，不重做无关用例或改写旧报告。问题每条一个决定：对象、条件、操作时点及所缺结果写清，避免“异常是否正常”等空问。相关问题可在自然文字中说明依赖，但不新增父子问题字段、负责人或确认状态。是否采纳、正式编号及同步逐条入库由平台和人工处理。
