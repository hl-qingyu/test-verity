# 角色、状态、入口与归属

## 先识别共同对象

多个页面或端参与同一订单、申请、账号或关系时，先确认它们是否指向同一业务对象。名称相似不证明同一对象，不同名称也不必然是不同对象；按资料中的身份关联、动作与状态确定。跨步骤使用唯一、可识别的对象称呼，不将标题字段当成对象本身。

有生命周期时检查来源状态、触发动作、执行角色和端、目标状态、观察角色及位置。下一步来源状态须能由上一步结果到达；缺转换或最终结果时说明具体缺口，不按常见审批流程补状态。普通字段和查询不强行套状态图。

## 入口与观察位置

明确系统有某规则，不代表当前端有“查看规则”“打开明细”入口。每个确定页面、按钮、详情、列表、弹窗和查询方法都应有当前目标端的需求、原型或批注支持。其他端入口不能移植；不能因为后台存在配置就编造App配置页。

业务结果明确、可观察方式未提供时，仍可生成待审阅设计，在data_requirements具体列出观察位置和权限待准备。steps只描述已明确的业务动作及待准备的核对任务，不伪装成存在的按钮、接口或SQL。只有业务上是否应提供展示或某角色是否有权执行本身不明确时才提BUSINESS_QUESTION。

同一功能不同身份拥有不同入口、字段、权限、数据范围或结果时分别设计，不能用“用户”合并为一条模糊路径。资料明确多个身份等价时可选一个具体执行身份作为代表，不扩展未证明的角色权限。

## 跨端协作与时序

已完成的外部动作可以作为初始状态，例如管理员已冻结账号；本条要验证的操作必须留在steps，例如被冻结账号再次提交请求。验证过程中发生的外部变化则写在实际时点：先填写、再由对应角色修改状态、再提交，不能改为开始前已经修改。

真实协作用例可以有多个角色及相关断言，每一步写清角色、端、共同对象、动作时点和观察位置。其他角色的独立权限或互斥路径应另写，不强制所有跨端断言拆成单结果，也不把不同对象和独立任务塞进一条。未选其他端只作为关联准备或依据，不自动生成其全部模块用例。

异步场景按明确时限或终态条件写等待与刷新/重进动作；未知时限不得填“立即同步”或任意秒数。明确有结果但观察方法缺失归执行准备；是否同步、何时生效会改变验收且没有规则时归业务问题。

## 模块与视角

module按所选功能和资料实际端/模块组织，structure按页面或子操作统一命名；有必要时注明角色视角。目录只帮助分类，不能定义预期。关联详情可以归属发起功能，不按文件名机械拆模块；分类尚未判断时继续理解，以资料中已有功能/业务操作组织候选，不能仅因分类工作未做完写UNFINISHED，也不编“未知模块”占位。真正缺少适用资料时按依据规则说明具体阻碍。页面移动、模块改名本身不证明业务取消，不据此RETIRE。
